# Unreleased — 2.0.0


### BREAKING CHANGES

Migration steps for each change: [docs/migration-2.0.md](docs/migration-2.0.md).

* **core:** a `spuriousWakeup` effect is refused unless its `NioSelector` lists `NIO_SELECTOR_SELECT` as its only operation; another NIO operation beside it was accepted, and the effect then skipped that channel call ([migration §42](docs/migration-2.0.md#42-spuriouswakeup-selects-nio_selector_select-alone)).

* **testkit, spring, micronaut, quarkus:** the `ChaosControlPlane` a test extension injects (`TrackingChaosControlPlane`) ends everything the test created through it: `stopTracked()` also closes the sessions it opened and removes the listeners it added, after each test (testkit) or test class (Spring Boot, Micronaut, Quarkus). A listener or session that a later test relied on is gone ([migration §41](docs/migration-2.0.md#41-a-tests-sessions-and-listeners-end-with-it)).

* **api, core:** an `ExceptionInjectionEffect` may name `java.` and `javax.` classes only (`jakarta.` and `com.macstab.chaos.jvm.` are refused when the effect is built), and the class is resolved at activation: a class the agent's class loader cannot find, a non-`Throwable`, a non-public or abstract class (`VirtualMachineError`) or one without a public `(String)` or no-argument constructor (`CompletionException`) fails the activation with `ChaosValidationException` instead of throwing something else from the woven method ([migration §36](docs/migration-2.0.md#36-injected-exceptions-are-jdk-classes-resolved-at-activation)).

* **instrumentation:** `EXECUTOR_SUBMIT` also covers `execute` / `submit` of a `ScheduledThreadPoolExecutor` and of the virtual-thread-per-task executor (`Executors.newVirtualThreadPerTaskExecutor()`), once per call; it covered `ThreadPoolExecutor.execute` only. An STPE's `execute` / `submit` is no longer a `SCHEDULE_SUBMIT` (its task still fires `SCHEDULE_TICK`), and a suppressed STPE or virtual-thread submission completes its future with `null` ([migration §35](docs/migration-2.0.md#35-executor_submit-covers-scheduled-and-virtual-thread-executors)).

* **api, instrumentation:** method hooks never weave a JDK class (one of the bootstrap or platform class loader), whatever a `MethodSelector` names: `exact("java.util.HashMap")` + `get` was woven into every `HashMap.get` of the JVM. A `MethodSelector` whose class and method patterns both match everything is refused with `IllegalArgumentException`, now also for a `GLOB` of `*` only (`glob("*")`, `glob(null)`) and the `REGEX` `.*`, `^.*$` and `.*+`, not only `ANY` (migration §34).

* **instrumentation, core:** the JDK's own use of a general primitive is no longer a target (semantics L3a, an enumerated list): class loading under `FILE_IO_*` and `ZIP_*` (a reject no longer breaks class loading), the JDK's temporary direct buffers under `DIRECT_BUFFER_ALLOCATE`, the collections `Bits.reserveMemory` and file mapping request under `SYSTEM_GC_REQUEST`, the `CompletableFuture` timers of `orTimeout` / `completeOnTimeout` (`SCHEDULE_SUBMIT` and `SCHEDULE_TICK` on JDK 21, `FORK_JOIN_TASK_RUN` on JDK 25, their completion under `ASYNC_COMPLETE*`; `delayedExecutor` stays evaluated), `/dev/random` and `/dev/urandom` for a `FileIoSelector` without a path pattern, the JDK `HttpClient`'s selector thread under `NIO_SELECTOR_SELECT`, `jdk.internal.*` futures, the JDK-private `ThreadLocal` classes and `ThreadPoolExecutor$Worker` for an `ANY` pattern, and the object streams' serialization hooks under `REFLECTION_INVOKE`. The agent's own MBeans are never a JMX target. A JMX event's subject is its `ObjectName`, an `ASYNC_*` event's target class the future's class, and `MBeanServer.getAttributes` is a `JMX_GET_ATTR` (migration §33).

* **instrumentation:** a client-library reject fails the call through the library's own failure channel. gRPC: `RPC_CALL` is evaluated when the call opens its stream (`newStream`), not at `ClientCallImpl.start`, and a reject opens no stream and fails the call through its listener with `UNAVAILABLE` (gRPC's `FailingClientStream`): a future stub's future and an async stub's observer receive it instead of a throw from the stub call. A gRPC whose `FailingClientStream` has no known constructor is refused at activation when visible. Netty: `NETTY_CHANNEL_WRITE` is evaluated at the channel's `doWrite`, not `flush0()`; a reject fails the flushed writes' futures and closes the channel, and an empty flush is no longer evaluated. A datagram channel's write is not evaluated: a real error there fails one datagram and keeps the channel open, and a reject closed every matching UDP channel (a NIO datagram write reaches `DATAGRAM_SEND`). Kafka: a `MESSAGE_SEND` reject fails the send through its callback, the interceptors and the future, as a metadata timeout does, instead of throwing from `send()`. Lettuce: a reject completes the command exceptionally (an async future fails, the sync API throws), and a batch sent through `dispatch(Collection)` is evaluated once by its first command. JDK `HttpClient.sendAsync`: a reject returns a failed future instead of throwing. OkHttp: evaluated in the call chain; an enqueued call's reject reaches `Callback.onFailure` on the dispatcher thread, and a request an interceptor sends is evaluated too. A reject ends the call as a network failure does (`noMoreExchanges`): `EventListener.callFailed` runs and the call timeout exits, so an expired `callTimeout` turns it into OkHttp's `InterruptedIOException`. Reactor Netty: evaluated once per subscription (each retry), and a reject is an error signal. R2DBC: a reject is signalled through the publisher `execute()` returns (migration §32).

* **instrumentation:** Apache HttpClient 4 and 5 are evaluated at `doExecute`, which every `execute` and `executeOpen` overload reaches once per request, instead of at the public `execute` overloads. A request sent from a response handler is now evaluated too (it ran inside the outer call's scope), and the URL follows one rule for every overload: an absolute request target, else the host's URI and the target, else the request's full URI (migration §31).

* **testkit:** `chaos-agent-testkit` no longer exports `junit-jupiter-api` or the JUnit BOM (it compiles against them only), so the modules built on it (the Spring Boot test starters, the Quarkus and Micronaut modules) put no JUnit on a production class path and force no JUnit version. Declare JUnit in your test dependencies (migration §29).

* **api:** `OperationType` gained constants next to their families (`CLOCK_READ`, `FILE_IO_OPEN`, `SOCKET_BIND`, `DATAGRAM_SEND`, …), so the ordinals of later constants moved; persist names, not ordinals.

* **instrumentation:** `SOCKET_*` scenarios also match `SocketChannel` and `ServerSocketChannel` calls: the JDK `HttpClient`, NIO clients and servers, and Spring's `TestRestTemplate` where it uses the JDK client. A `NetworkSelector` without peer filters now also reaches those connections; narrow it with `remoteCidr` / `remotePort` where only one peer is meant.

* **api:** `ChaosControlPlane.removeEventListener` and `bindSession` and `ChaosActivationHandle.matchedCount()` / `appliedCount()` are new abstract methods; custom implementations must add them.
* **core:** a clock-skew scenario whose policy sets `maxApplications`, `rateLimit`, `activateAfterMatches` or `probability < 1.0` is rejected with `ChaosValidationException`; 1.x ignored those fields for clock skew. `ActivationPolicy.fromJson` takes `activeFrom` and `activeUntil`.
* **instrumentation:** hooks are woven on demand. The agent no longer weaves every hook at start: each interception point belongs to a hook group (`JdkInstrumentationInstaller.HookGroup`) that is retransformed the first time an activated scenario (or an opened session) needs one of its operation types, and stays woven until uninstall. A JVM without scenarios runs unmodified JDK classes; the first activation of a hook group pays its one-time weaving cost, and a weaving failure fails that activation with failure category `INSTRUMENTATION_FAILURE`. The agent argument `instrumentation=eager`, the system property `-Dmacstab.chaos.instrumentation=eager` or the environment variable `MACSTAB_CHAOS_INSTRUMENTATION=eager` restores the 1.x behaviour (every group woven at start).
* **instrumentation:** the premain / agentmain split is gone. Dynamic attach (`agentmain`, still behind its opt-in) and `installForLocalTests()` get exactly the same hook set as `-javaagent:` — sockets, NIO, HTTP, JDBC, clock and the rest are no longer premain-only. `ChaosAgentBootstrap.initialize(agentArgs, instrumentation, environment)` lost its `premainMode` parameter, and `JdkInstrumentationInstaller.install` takes an `eager` flag instead.
* **instrumentation:** the unused handle slot `ADJUST_SCHEDULE_DELAY` (index 5) and `BridgeDelegate.adjustScheduleDelay` were removed. Every `BootstrapDispatcher` handle index above 5 shifted down by one; new slots were appended. The slot `RESOLVE_SHUTDOWN_HOOK` and `BridgeDelegate.resolveShutdownHook` (the identity) were removed with the `removeShutdownHook` advice, `BEFORE_SOCKET_SHUTDOWN` moved to the freed index 12, and `decorateShutdownHook` returns `void` (the hook was always registered as itself). The slots `IDLE` (`BridgeDelegate.idle(String)`, index 76) and `AFTER_PROCESS_START` (`afterProcessStart(Object, String)`, 77) were appended; `HANDLE_COUNT` is 78.
* **packaging:** the agent JAR (`chaos-agent-bootstrap`) relocates ByteBuddy and Jackson to `com.macstab.chaos.jvm.shaded.*`, so they can no longer clash with the application's own copies (Mockito, Hibernate, Spring). Its published POM declares no dependencies: everything it needs is inside the JAR. The Spring Boot starters no longer depend on `chaos-agent-core` and `chaos-agent-startup-config` at runtime; those classes come from the agent JAR.
* **api:** `chaos-agent-api` no longer depends on `jackson-annotations`. The JSON shape of plans (the `type` discriminators, the `ActivationPolicy` and `NamePattern` creators) is defined by mix-ins in `chaos-agent-startup-config`; serialise and parse plans with `ChaosPlanMapper`, another `ObjectMapper` no longer knows the discriminators.
* **api:** a GLOB is matched by code points: `*` matches any sequence, line terminators included (in 1.x it stopped at a line break while `?` did not), and `?` exactly one character, a surrogate pair counting as one. Globs no longer compile a regex; they match without allocating. Use a REGEX where a pattern must not cross a line break.
* **spring:** `/actuator/chaos` answers with the outcomes and HTTP statuses of the Micronaut and Quarkus endpoints (400 `invalid`, 409 `conflict`, 422 `rejected`, 404 `not-found`, 409 `unmanaged`) instead of 200 with `status = "error"`, and stops only the plans activated through it, not the startup plan. On Spring MVC its request body is capped before it is bound: above 2 MiB + 64 bytes (a 1 MiB plan, escaped) it is refused with 413, decided from `Content-Length` or while reading; Spring MVC read any body into memory first. On WebFlux `spring.codec.max-in-memory-size` (256 KiB by default) bounds it; raise it to `2MB` for plans up to the 1 MiB plan cap.
* **core:** a `reject` on `EXECUTOR_WORKER_RUN` or `FORK_JOIN_TASK_RUN` is refused at activation. It threw on the pool worker before the pool recorded the task: the worker died and the task's future never completed.
* **core:** a `reject` or `suppress` on `QUEUE_OFFER` no longer answers `false` from a queue without a capacity limit (`remainingCapacity()` is `Integer.MAX_VALUE`); the offer runs and counts no application. A thread pool built on an unbounded queue (`Executors.newFixedThreadPool`) can no longer be saturated through `QUEUE_OFFER`; reject `EXECUTOR_SUBMIT`.
* **core:** a task submitted to a thread pool from a session is wrapped to carry the session only once the session has a registered scenario. A pool task submitted from a session without scenarios runs outside any session, so the HTTP calls it makes no longer carry `X-Chaos-Session`; activate a scenario in the session before submitting, or set the header from `session.id()`.
* **core:** a `reject` on `QUEUE_TAKE` or `QUEUE_POLL` is refused at activation. `take()` and `poll()` fail only by interruption, and a thread pool's worker taking its next task died on the thrown exception and was replaced, over and over: thousands of threads a second, and no task ran. Delay or gate them, suppress `QUEUE_POLL`, or reject `QUEUE_PUT` / `QUEUE_OFFER`.
* **quarkus, micronaut:** a switch that enables fault injection or a management endpoint (`macstab.chaos.enabled`, `macstab.chaos.management.enabled`, `macstab.chaos.management.allow-anonymous`) is honoured only from a launch-time local source (system properties, environment variables, the application's own config files, test properties), as the Spring starters already required; a config server needs `macstab.chaos.allow-remote-enable=true` set locally. Quarkus reads `macstab.chaos.enabled` at run time only: the switch is no longer needed at build time, and the `ChaosControlPlane` bean is always registered (used without the switch and without an installed agent it fails with `IllegalStateException`). A test composing `@MicronautTest` and `ChaosMicronautExtension` itself adds `@Property(name = "macstab.chaos.test.enabled", value = "true")` for the tracking control plane; a plain `@MicronautTest` no longer gets it. `ChaosFactory.chaosControlPlane` takes the `Environment`. Every switch reads `true|false|1|0|yes|no|on|off`, any other value is off with a warning.
* **core:** a `directBufferPressure` above the JVM's direct memory limit (`-XX:MaxDirectMemorySize`, by default the maximum heap) is refused at activation with `ChaosUnsupportedFeatureException` (`UNSUPPORTED_RUNTIME`); it used to fail with an unrecorded `OutOfMemoryError`.
* **testkit, spring, micronaut, quarkus:** `@WithChaos` scenarios are active around the test method only: the extensions activate them in `beforeTestExecution` and stop them in `afterTestExecution`, so the test's `@BeforeEach` and `@AfterEach` methods no longer run under them (testkit: class- and method-level; Spring Boot 3/4, Micronaut, Quarkus: method-level and Quarkus `@ChaosScenario` on the method; their class-level declarations still span the class). The testkit binds the thread that runs the test method, so a `@Timeout(threadMode = SEPARATE_THREAD)` body and the dynamic tests of a `@TestFactory` run in the session. The framework extensions implement `BeforeTestExecutionCallback` / `AfterTestExecutionCallback` instead of `BeforeEachCallback` / `AfterEachCallback`.
* **api:** `ActivationPolicy.fromJson` is private: it is the JSON creator the plan mapper binds, not an API. Build policies with the constructor or `ActivationPolicy.builder()`, or read JSON with `ChaosPlanMapper`.
* **bootstrap:** the JFR event `com.macstab.chaos.jvm.ScenarioLifecycle` names its field `message`, not `description`: it holds the event's message ([migration §40](docs/migration-2.0.md#40-the-jfr-field-description-is-message)).
* **startup-config:** a `gate` without `maxBlock` is refused by the plan reader with `ConfigLoadException`, for every JSON source (plan file, startup JSON, HTTP, JMX, `@WithChaos`): only an activation handle releases a gate, and a JSON plan's author holds none, so the gate held its callers until the scenario was stopped. The `randomSeed` default is documented as the code applies it: a policy without a seed draws a random one, a scenario without a policy has seed 0 ([migration §39](docs/migration-2.0.md#39-a-gate-read-from-json-needs-maxblock)).
* **startup-config:** plan JSON is read strictly: a duration or instant given as a number, a number given as a string, a fraction for an integer, `0`/`1` for a boolean, an enum ordinal and a field given twice are refused with `ConfigLoadException` (1.x read `1e100` as a zero duration and kept the last of two values). Durations and instants are written as ISO-8601 strings, also `capturedAt` in the diagnostics the management endpoints return, and `ChaosPlanMapper.write` leaves out absent values.
* **api:** `NamePattern` refuses a mode other than `ANY` without a value (`{"mode": "GLOB"}`, `glob(null)`), a value without a mode and `ANY` with a value other than blank or `"*"`, with `IllegalArgumentException`; 1.x turned each into a pattern matching everything. The REGEX and CIDR caches are emptied when full and cache the new entry, instead of compiling or parsing every new entry on each match once full.
* **api:** every production package is JSpecify `@NullMarked`, and the parameters that accept `null` (the patterns of the selector constructors and factories, `ChaosScenario`'s description, scope and policy and their builder setters, `ChaosPlan`'s metadata and observability, `NamePattern`'s mode and value) are `@Nullable`, while the values they normalise to are not. Kotlin sees the API's types as non-null instead of platform types: code that passed or expected `null` where the type now says non-null no longer compiles.
* **api:** the legacy duplicate package tree `com.macstab.chaos.*` (everything outside `com.macstab.chaos.jvm.*`) was removed. Use the `com.macstab.chaos.jvm.*` types.
* **api, core:** a `suppress` on `HTTP_CLIENT_SEND`, `HTTP_CLIENT_SEND_ASYNC` or a `JDBC_*` operation is refused at activation with `ChaosValidationException` ("use reject"). It threw `ChaosHttpSuppressException` / `ChaosJdbcSuppressException`, which no real client throws (ADR 0005); both classes are removed. Use `reject`, which fails the call with the client's own `IOException` / `SQLException`. `BootstrapDispatcher.beforeHttpSend`, `beforeHttpSendAsync` and the five `beforeJdbc*` (and the matching `BridgeDelegate`, `ChaosRuntime` and `ClientDispatch` methods) return `void`.
* **core:** a `reject` raises the exception the real call raises, and every injected failure's stack trace starts at the intercepted method (the agent's frames are removed): `DNS_ANSWER` `UnknownHostException`, `NIO_SELECTOR_SELECT` `IOException`, a socket read without `SO_TIMEOUT` (and every socket-channel read) `SocketException`, `SOCKET_WRITE` `SocketException`, `ZIP_INFLATE` `DataFormatException`, `REFLECTION_INVOKE` `InvocationTargetException` with a cause, `SCHEDULE_SUBMIT` `RejectedExecutionException`, `EXECUTOR_AWAIT_TERMINATION` and `QUEUE_PUT` `InterruptedException`, a platform `THREAD_START` the JVM's `OutOfMemoryError("unable to create native thread: …")`, `SHUTDOWN_HOOK_REGISTER` `IllegalStateException("Shutdown in progress")`, a `java.nio` `FILE_IO_OPEN` `FileSystemException`, and a client library call whose library type is not visible `IOException`; `METHOD_ENTER`, `METHOD_EXIT` and `SCHEDULE_TICK` keep `IllegalStateException`. A file errno on a read, write, truncate, map or close is `IOException("<reason>")`, not a `FileSystemException` naming the path, and an errno is refused at activation on a call the kernel never reports it for (`ENOENT` on a read, `EROFS` on a truncate, `ENOSPC` on a delete).
* **core:** a `reject` is refused at activation with `ChaosValidationException` where no real call fails that way: `THREAD_PARK`, `MONITOR_ENTER`, `SYSTEM_GC_REQUEST`, `SYSTEM_EXIT_REQUEST`, `THREAD_LOCAL_GET`, `THREAD_LOCAL_SET`, `ASYNC_CANCEL`, `ZIP_DEFLATE` and `EXECUTOR_SHUTDOWN` (it threw an `IllegalStateException` or `RuntimeException` no real call throws). Each refusal names what to use instead. `METHOD_ENTER`, `METHOD_EXIT` and `SCHEDULE_TICK` still take a reject.
* **core:** the destructive-effect refusal (`DeadlockEffect` or `ThreadLeakEffect` without `allowDestructiveEffects`) is a `ChaosValidationException`, like every other validation error; it was a `ChaosActivationException`. Over HTTP and JMX the outcome stays `invalid`; its message starts with `invalid plan:` instead of `plan rejected:`.
* **core:** retroactive entries for changes made earlier in 2.0: a stress scenario whose policy sets `maxApplications`, `rateLimit`, `activateAfterMatches`, `probability < 1.0`, `activeFrom` or `replayMatches` is refused (a stressor runs from start until stop, `activeFor` or `activeUntil`); a `suppress` on an operation that cannot be skipped is refused (the list is in the configuration reference); a clock read takes only a clock skew, and a clock skew applies only to clock reads.
* **core:** stressor parameters are refused instead of reduced silently: `heapPressure` above the free heap (the maximum heap less what is in use) with `ChaosUnsupportedFeatureException` (`UNSUPPORTED_RUNTIME`; it was capped at half the heap with a warning); `stringInternPressure` above 1,000,000 strings, 1 MiB per string, or more strings than 256^`stringLengthBytes` (clamped, or duplicated, before) and a `floodInterval`, `gcInterval` or `heartbeat` below 1 ms (it spun) with `ChaosValidationException`.
* **core:** the `@Internal` `ChaosRuntime` overloads that nothing in the agent called are removed: `beforeThreadStart(Thread)`, `beforeSocketRead(Object)`, `beforeSocketWrite(Object, int)` and `beforeFileIo(String, Object)`. Call the full forms (`beforeThreadStart(thread, false)`, `beforeSocketRead(stream, len, address, port, soTimeout)`, `beforeSocketWrite(stream, len, address, port)`, `beforeFileIo(operation, stream, path, byteCount)`). The documented manual hooks `beforeMethodEnter(String, String)` and `afterMethodExit(String, String, Class, Object)` stay.
* **testkit:** `ChaosAssertions`: `within(t).never()` and `within(t).atMost(n)` hold for the whole of `t` (they checked once); `hasNoFailuresFor` takes at least one id and tolerates a repeated one (it threw `IllegalArgumentException`); a negative bound or timeout is refused; messages name every scenario `<scopeKey>::<id>`; count failures carry the expected and actual values; a `within` of any length is accepted (centuries threw `ArithmeticException`); and the waiting is invisible to `THREAD_SLEEP` scenarios (they counted and delayed every 10 ms poll).
* **api:** `ChaosEvent.Type` gained `INACTIVE`, published once when a scenario ends on its own (`reason` `expired` or `max applications reached`); a `switch` over `ChaosEvent.Type` without a `default` must handle it ([migration §30](docs/migration-2.0.md#30-chaoseventtypeinactive-and-one-event-per-transition)).

* **core:** a stressor that this JVM's flags leave without load is refused at activation with `ChaosUnsupportedFeatureException` (`UNSUPPORTED_RUNTIME`; HTTP/JMX `rejected`): a `safepointStorm` with `retransformClassCount = 0` under `-XX:+DisableExplicitGC`, and a `finalizerBacklog` under `--finalization=disabled`. Both were accepted and produced nothing. ZGC, Shenandoah and `-XX:+ExplicitGCInvokesConcurrent` are not refused (shorter pauses), nor is `referenceQueueFlood` under `-XX:+DisableExplicitGC` (fewer references processed) ([migration §37](docs/migration-2.0.md#37-stressors-without-load-are-refused-and-a-stressor-that-stops-ends-its-scenario)).

* **core:** the event log line is `type=X scenarioId="…" message="…" attributes={k="v", …}`: the id, message and attribute values are quoted, and the id, message, keys and values escaped (`\\`, `\"`, `\r`, `\n`, `\uXXXX` for the other control characters and U+2028/U+2029). It was `type=X scenarioId=… message="…" attributes={k=v, …}`, unescaped. A parser of the old line must follow ([migration §38](docs/migration-2.0.md#38-the-event-log-line-is-quoted-and-escaped)).

### Changed

* **bootstrap, spring, micronaut, quarkus:** the `message` of a management activation answer (HTTP and JMX) starts with one prefix per outcome: `invalid plan:` for every `invalid` answer (also a blank plan, and an activation failure that is neither a validation error nor a conflict, which said `plan rejected:`), `plan conflict:` for `conflict` (it said `plan rejected:`), and `plan rejected:` only for `rejected`. Every log line and printed warning of the agent and its integrations starts with `[chaos-agent] ` (most said `chaos-agent: `), and a missing agent is "the chaos agent is not installed" everywhere.

* **startup-config:** a `file:` source (the status file's `source=`, `LoadedPlan.source()`, `ConfigLoadException.getSource()`) is the plan file's absolute, normalised path, also when it was configured relative.

### Features

* **bootstrap:** the `bridgeDir` setting (`-Dmacstab.chaos.bridgeDir`, `MACSTAB_CHAOS_BRIDGE_DIR`) names the directory for the bootstrap bridge jar. It must be neither world-writable without the sticky bit nor another user's, with no directory above it world-writable without the sticky bit or another user's and no link on the configured path another user's (POSIX), and the jar is created, written and opened at the real path the check resolved, so a link re-pointed after the check moves nothing; a refused or unwritable `bridgeDir` aborts the start with the reason, it is never replaced by another directory.
* **core:** a session-scoped scenario may select thread starts and sleeps (`ThreadSelector`) and executor shutdowns (`ShutdownSelector` on `EXECUTOR_SHUTDOWN` / `EXECUTOR_AWAIT_TERMINATION`): they run on the session's thread. Only the operations the JVM evaluates without a session (`CLASS_LOAD`, `CLASS_DEFINE`, `RESOURCE_LOAD`, `SHUTDOWN_HOOK_REGISTER`) and stressors are refused in a session.
* **build:** `chaos-agent-bom` aligns the versions of every published module: import it as a platform (Gradle) or in `dependencyManagement` (Maven) and declare the modules without versions.
* **spring:** built and tested against Spring Boot 3.5.16 and 4.1.2 (were 3.5.13 and 4.0.5).
* **instrumentation:** hook health in the diagnostics: `unmatchedHooks` lists hooks woven into a type that matched none of its methods (a JDK or library release changed the method, so the hook is inactive), `hookFailures` the types whose weaving failed.

* **instrumentation:** the rest of the native io and net operations: `FILE_IO_CLOSE` (evaluated after a stream, `RandomAccessFile` or `FileChannel` closed, so a failing close still releases the descriptor; one event for a stream and its channel), `FILE_IO_MOVE_TARGET` (a move or rename by its destination), `SOCKET_SHUTDOWN` (`shutdownInput` / `shutdownOutput`), and `PROCESS_WAIT` (`Process.waitFor`). `ChaosEffect.timeout()` also applies to `select(timeout)`, which then waits it out and reports no ready channel, and to a timed `waitFor`, which reports a child that has not exited. `ChaosEffect.Errno` gains `EINVAL`, `EOPNOTSUPP`, `EAFNOSUPPORT` and `EPROTONOSUPPORT`.

* **api:** `ChaosPresets`: ready-made scenarios for common faults — `diskFull`, `failingDisk`, `fsyncFailure`, `slowDisk`, `tooManyOpenFiles`, `connectionRefused`, `connectionResets`, `slowNetwork`, `trickledResponses`, `packetLoss`, `failover`, `dnsOutage`, `clockJump`, `threadExhaustion` — each a prefilled `ChaosScenario.Builder` tagged `preset=<name>`, so scope and policy stay the caller's.

* **api:** `ChaosEffect.redirect(host[, port])` (JSON `redirect`) sends a `SOCKET_CONNECT` of a `Socket` or `SocketChannel` to another endpoint: a failover target, a black hole, a slow proxy. Without a port the requested one is kept.

* **instrumentation:** UDP: `DATAGRAM_SEND` and `DATAGRAM_RECEIVE` cover `DatagramSocket` and `DatagramChannel` by destination or connected peer and datagram length. `suppress()` drops a datagram silently (packet loss), `corruptRead()` flips one bit of a datagram received, `ECONNREFUSED` is `PortUnreachableException`. New hook group `DATAGRAM`.
* **instrumentation:** reverse lookups are the new `DNS_REVERSE` (`InetAddress.getHostName`, `getCanonicalHostName`), matched by the IP literal; a rejection returns the literal, as the JDK reports a failed lookup.

* **instrumentation:** memory-mapped files and transfers: `FileChannel.map` is the new `FILE_IO_MAP` (sized by the region; `ENOMEM` fails with `IOException("Map failed")`), `MappedByteBuffer.force` is a `FILE_IO_SYNC` failing with `UncheckedIOException`, `FileChannel.transferTo` / `transferFrom` are one `FILE_IO_READ` / `FILE_IO_WRITE` each (a torn `transferFrom` is short; the JDK's internal reads and writes of a transfer are not evaluated again), and `Files.copy(Path, Path)` opens its source and target (`FILE_IO_OPEN`).

* **instrumentation:** clock skew reaches every `java.time` read: the new `CLOCK_READ` is a read of the system `Clock` (`Clock.systemUTC()`, `systemDefaultZone()`, `InstantSource.system()`), and so of every `now()` without an operation of its own (`LocalDate`, `LocalTime`, `OffsetDateTime`, `OffsetTime`, `Year`, `YearMonth`, `MonthDay`) and of clocks derived from the system clock. Before, those reads were never skewed. The read inside `LocalDateTime.now()` and `ZonedDateTime.now()` stays theirs, so selecting both never skews twice.

* **instrumentation:** file opens are the new `FILE_IO_OPEN`: the `FileInputStream`, `FileOutputStream` and `RandomAccessFile` constructors (failing with the JDK's `FileNotFoundException("<path> (<reason>)")`) and the platform file system's `newByteChannel` / `newFileChannel` behind `Files.newInputStream`, `newOutputStream`, `newBufferedReader` and `FileChannel.open`. Opens of class-path archives are never evaluated.
* **instrumentation:** binds are the new `SOCKET_BIND` (every socket and socket-channel bind, through `sun.nio.ch.Net.bind`); `NetworkSelector` address filters match the local address being bound, errors are `BindException`.
* **api:** `ChaosEffect.Errno` gains `EADDRNOTAVAIL`, `ENOTCONN`, `ENOBUFS` and `ENFILE`. `EMFILE` and `ENFILE` also apply to socket connects and accepts (an accept fails with `IOException("Too many open files")`), `EACCES` to binds, and `EAGAIN` / `ENOMEM` to a platform `THREAD_START`, which then fails with the JDK's `OutOfMemoryError: unable to create native thread`.

* **instrumentation:** socket channels are sockets. `SocketChannel` connect, reads and writes (also scattering and gathering) and close, and `ServerSocketChannel.accept`, raise the `SOCKET_*` events with the channel's peer and byte count, so `NetworkSelector` peer and size filters and the data effects reach NIO clients: `trickle` limits the buffers, `corruptRead` flips one bit of what the read returned, `tornWrite` is a short count, `connectionReset` closes with `SO_LINGER` 0. A Unix-domain channel's peer is its path, matched by the host pattern (the native `unix://` endpoint). The `NIO_CHANNEL_*` events still fire as before. New hook group `SOCKET_CHANNEL`.
* **instrumentation:** scattering and gathering `FileChannel` reads and writes (`ByteBuffer[]`) are `FILE_IO_READ` / `FILE_IO_WRITE` events over all their bytes, with `tornWrite` and `corruptRead`; gathering socket-channel writes are torn by `NIO_CHANNEL_WRITE` as single ones are.

* **demos:** `demo/` holds one-fault demos (connect refused, trickle, disk full by path, DNS override, clock skew, process start fails, HTTP reject, slow executor), each a single-file program with its plan and expected output; `demo/run-all.sh` runs and checks them, and CI runs it.
* **micronaut, quarkus:** management endpoints matching the Spring actuator: Micronaut `@Endpoint("chaos")` (`ChaosManagementEndpoint`, with `micronaut-management`) and the Quarkus route `/q/chaos`, both off unless `macstab.chaos.management.enabled=true`; snapshot, activate a plan, stop one, stop all. The Quarkus route is the separate extension `chaos-agent-quarkus-management` and answers 401 to a request without an authenticated user unless `macstab.chaos.management.allow-anonymous=true`.
* **sessions across HTTP:** requests the JDK `HttpClient` and `HttpURLConnection` send from a thread in a session carry `X-Chaos-Session` (`ChaosSession.HEADER`); `ChaosControlPlane.bindSession(id)` binds a server thread to that session for a request, and the Spring Boot test starters register `ChaosSessionFilter`, the runtime starters only together with `macstab.chaos.enabled` (switch: `macstab.chaos.session-propagation.enabled`). The id decides per request: an unknown or closed id runs the request outside any session, even on a worker thread that inherited one. Session-scoped scenarios thereby reach the server side of `@SpringBootTest` HTTP calls.
* **api:** decision replay: `ChaosDecisionRecorder` records which match numbers of each scenario took effect (from the new `match` attribute of `APPLIED` events), and `ActivationPolicy.replayMatches` (JSON `replayMatches`) makes a scenario fire on exactly those matches instead of drawing, so an unseeded flaky run replays decision by decision. `recorder.replay(scenario)` builds the replaying scenario. The policy record gains the trailing `replayMatches` component; the 10-argument constructor is kept.
* **instrumentation:** clock skew for direct `System.currentTimeMillis()` / `System.nanoTime()` calls. With the agent setting `clockCallSites=<package prefixes>` (also `-Dmacstab.chaos.clockCallSites`, `MACSTAB_CHAOS_CLOCK_CALL_SITES`), the agent rewrites those calls in the named packages to read the clock through `SYSTEM_CLOCK_MILLIS` / `SYSTEM_CLOCK_NANOS` once such a scenario is activated; the intrinsics themselves cannot be advised. JDK prefixes are refused.
* **instrumentation:** process starts: `ProcessBuilder.start`, `startPipeline` and `Runtime.exec` are `PROCESS_START` events, selected with `ChaosSelector.process(commandPattern)` (JSON `"process"`) by program. A reject throws `IOException`; an `errno` throws the JDK's own `Cannot run program "x": error=N, reason`. `ChaosEffect.Errno` gains `EAGAIN` and `ENOMEM` (process family), `code()` (the error's number on the running OS, as the JDK prints it) and `linuxCode()`.
* **quarkus:** `@ChaosScenario` (and its container `@ChaosScenarios`) is deprecated for removal in 3.0 in favour of the testkit's `@WithChaos`, which `ChaosQuarkusExtension` honours with the full plan JSON model.
* **observability:** new optional module `chaos-agent-opentelemetry`: `ChaosOpenTelemetry.metrics(controlPlane, openTelemetry)` publishes the chaos metrics through the OpenTelemetry API, and `ChaosOpenTelemetry.spanEvents(controlPlane)` adds a `chaos.applied` event to the current span whenever chaos applies to a traced call.
* **observability:** new metrics `chaos.applications` (by operation and effect), `chaos.injected.delay` (the latency chaos added), `chaos.skips`, `chaos.activation.failures`, `chaos.listener.events.dropped` and `chaos.hooks.woven`; `APPLIED` events carry `delayNanos`. Tag values are lower case: `operation` is the `OperationType` name, `effect` the effect's plan JSON type (`delay`). `ChaosMeterBinder` is `AutoCloseable`; `ChaosOpenTelemetry.metrics` and `spanEvents` return a `ChaosOpenTelemetry.Registration`, whose `close()` throws no checked exception.
* **startup-config:** a plan's `observability` block now takes effect for its scenarios: `jmxEnabled=false` leaves them out of the JMX `listScenarios` and `debugDump`, `structuredLoggingEnabled=false` stops logging their events, `debugDumpOnStart=true` prints the diagnostics once the plan is active. It applies to programmatic plans, plan files (also across reloads) and JMX `activatePlan`; before, the block was parsed and ignored.
* **instrumentation:** file truncation, deletion and moves: `FILE_IO_TRUNCATE` (`FileChannel.truncate`, `RandomAccessFile.setLength`), `FILE_IO_DELETE` (`Files.delete`, `Files.deleteIfExists`, `File.delete`) and `FILE_IO_MOVE` (`Files.move`, `File.renameTo`, by source path), with path filters and the file `errno` values. `File.delete` and `File.renameTo` report an injected failure by returning `false`, as `java.io` does.
* **api:** `tornWrite()` also tears socket writes: a `SocketChannel` write returns a short count, a socket stream write sends a random prefix and then throws `SocketException` ("Connection reset …"), so the peer sees a truncated message. `SocketChannel` writes now report their byte count.
* **testkit:** `@WithChaos` declares a test's chaos in the plan JSON model, inline or from a class-path resource, as a whole plan or one scenario; repeatable, on classes and methods. Session-scoped scenarios run in the test's session, JVM-scoped ones on the control plane, and both stop with the test (method) or test class. Honoured by the testkit `ChaosAgentExtension` (which then binds the test thread to the session), the Spring Boot 3/4 test extensions (new `beforeEach`/`afterEach` for method-level annotations), `ChaosMicronautExtension` and `ChaosQuarkusExtension`. `WithChaosSupport` is the shared, public implementation.
* **testkit:** `ChaosAssertions` — `assertThat(handle).applied().atLeast(n)`, `exactly`, `atMost`, `never`, `within(Duration)` for effects on other threads, `matched()`, `hasState`, and on diagnostics `hasNoFailures()`, `hasNoFailuresFor(ids...)` and `scenario(id)`; failures are opentest4j `AssertionFailedError`.
* **api:** `ActivationPolicy` gains an absolute wall-clock window, `activeFrom` and `activeUntil` (JSON: ISO-8601 instants), read from the real system clock so an injected clock skew cannot move it; the equivalent of the native library's `@from`/`@until`. New factories `ActivationPolicy.count(n)` (`@first=N`) and `ActivationPolicy.window(from, until)`, and builder methods `activeFrom`, `activeUntil` and `window` (a stressor accepts `activeUntil` but refuses `activeFrom`). The 8-argument constructor is kept.
* **api:** DNS answer effects: the new `DNS_ANSWER` operation (when `InetAddress.getAllByName` returns or fails) with `dnsAnswer` — override with IP literals even when the lookup failed (`OVERRIDE`; `dnsOverride(address, moreAddresses...)` takes at least one), keep one address family (`FILTER_FAMILY`), shuffle (`SHUFFLE`), limit (`LIMIT`) — and `dnsRewrite(host)` on `DNS_RESOLVE`, which resolves another name (`REWRITE`).
* **instrumentation:** file coverage beyond streams: `RandomAccessFile` and `FileChannel` reads and writes are `FILE_IO_READ` / `FILE_IO_WRITE` events with their path and byte count, and fsync (`FileChannel.force`, `FileDescriptor.sync`) is the new `FILE_IO_SYNC`, failing with `SyncFailedException`. `ChaosEffect.tornWrite()` makes a `FileChannel` write succeed short (`TORN`). `RandomAccessFile` reads of `.jar` / `.zip` / `.jmod` archives are never evaluated: they are class loading.
* **api:** data-delivery effects, the native library's network effects on the real socket and file calls: `trickle(maxBytes)` caps each socket read (`TRICKLE`), `corruptRead()` flips one bit of the bytes a socket or file read returned (`CORRUPT`), `timeout()` waits out the socket's own `SO_TIMEOUT` or connect timeout and throws `SocketTimeoutException`, never firing on an infinite timeout (`TIMEOUT`), and `connectionReset()` closes with `SO_LINGER` 0 so the peer sees a reset (`RESET`).
* **api:** `ChaosEffect.errno(Errno)` — the native library's `ERRNO` effect as typed Java exceptions: network errors (`ECONNREFUSED`, `ETIMEDOUT`, `ECONNRESET`, `EHOSTUNREACH`, `ENETUNREACH`, `EPIPE`, `EADDRINUSE`) become the matching `java.net` exceptions; file errors (`ENOSPC`, `EDQUOT`, `EROFS`, `EACCES`, `ENOENT`, `EIO`, `EMFILE`) become `FileSystemException` subclasses carrying the file's path and the system's reason text.
* **api:** `ClockSkewMode.REGRESS` — the clock steps back once by `skewAmount` and stays shifted (the first read in the window arms it, the next one jumps), the native library's `REGRESS`.
* **instrumentation:** client-library hooks with their own operations and selectors: Kafka (`MESSAGE_SEND` / `MESSAGE_RECEIVE`, `messaging` selector by topic), gRPC (`RPC_CALL`, `rpc` by full method name), Jedis and Lettuce (`REDIS_COMMAND`, `redis` by command), R2DBC (`R2DBC_STATEMENT_EXECUTE` in the `jdbc` selector), the AWS SDK for Java v2 (`AWS_SDK_CALL`, `awsSdk` by service and operation) and Netty (`NETTY_CHANNEL_WRITE` / `NETTY_CHANNEL_READ`, `netty` by peer, including the native transports). A reject throws the library's own exception type. The libraries are matched by name; none is a dependency of the agent.
* **instrumentation:** `java.net.HttpURLConnection` and `HttpsURLConnection` requests are `HTTP_CLIENT_SEND` events (once per request, however the connection is driven), which covers Spring's `RestTemplate` default transport and the AWS SDK URL-connection client. A suppressed request fails with `java.net.ConnectException`.
* **instrumentation:** `MethodSelector` scenarios weave themselves. Activating one weaves entry and exit hooks into every concrete method its class and method patterns name (loaded classes are retransformed, later ones woven at load); removing it restores the original bytecode. One transformer covers all registered method selectors, so overlapping selectors weave a method once. `signaturePattern` now works: it is matched against the JVM method descriptor. The manual hooks remain for use without the agent.
* **api:** call-context filters, the equivalents of the native library's address, path and `@size` qualifiers. `NetworkSelector` gains `remoteCidr` (IPv4/IPv6 CIDR, parsed without DNS), `remotePort`, `minBytes` and `maxBytes`; `FileIoSelector` gains `pathPattern` (`PathPattern.under(dir)`, `/`-boundary prefix on the lexically normalised path), `minBytes` and `maxBytes`. Socket reads now report the bytes requested and every socket operation reports the peer port; file reads and writes report their path and byte count. The previous constructors are kept.
* **core:** clock-skew scenarios honour `activeFor`, `activeFrom` and `activeUntil`, and stressors end at `activeUntil` (a stressor refuses `activeFrom`: it runs from its activation).
* **diagnostics:** `ChaosDiagnostics.snapshot().runtimeDetails()` contains `wovenHookGroups` — the comma-separated, sorted names of the hook groups woven so far (empty when none).


* **observability:** status and hits files in the native library's line format, with the differences listed in observability.md §1 (`<tmpdir>/.chaos-jvm.status` after every load and reload, with `line`/`column`/`reason` for a rejected plan; `<tmpdir>/.chaos-jvm.hits.<pid>` with each scenario's applied count), written when switched on with `reports=on`, relocatable with `reportsDir`.
* **events:** `REGISTERED`, `SKIPPED` (with the policy check as `reason`, published while a listener is registered) and `FAILED` (activation failures with their `category`) are now published; `ChaosEventListener.async(listener)` delivers on an agent-owned thread through a bounded queue (`droppedEvents` in the diagnostics); `ChaosControlPlane.removeEventListener`.
* **observability:** `ChaosActivationHandle.matchedCount()` / `appliedCount()`; the MBean gains `listScenarios`, and — behind the opt-in `jmxControl=true` — `activatePlan(json)`, `stopScenario(id)` and `stopAll()`; new optional module `chaos-agent-micrometer` (`ChaosMeterBinder`).

* **startup-config:** reload robustness: changes are detected by the resolved file, modification time, size, file key and a SHA-256 of the contents (a touch reloads nothing; a rewrite in the same timestamp tick is caught by re-reading provisional reads made within 20 ms of the modification); broken contents keep the current plan and are parsed once; a removed config file stops its scenarios and removes the status file; Kubernetes ConfigMap and Secret mounts (`<name>` → `..data/<name>`) are followed, every other symbolic link is still rejected.

* **sessions:** a session now follows work handed off from a bound thread to `ForkJoinPool` tasks (submissions and forks — `CompletableFuture.*Async`, parallel streams), threads started with `Thread.start()` and virtual threads (`newVirtualThreadPerTaskExecutor` too), not only executor submissions.
* **startup-config:** the plan format is specified: `docs/plan-schema.md` and a JSON Schema (draft 2020-12) published in the agent as `com/macstab/chaos/jvm/startup/chaos-plan.schema.json`, for editor completion and validation. It is generated from `ChaosPlanMapper`, so it matches what the parser accepts.
* **api:** nullness is part of the types: the optional parts of the API (policy bounds, selector filters, DNS and redirect options, `NamePattern.matches(null)`, `bindSession(null)`) are JSpecify `@Nullable`, everything else is non-null. `chaos-agent-api` publishes the JSpecify annotations as its one dependency; the agent jar leaves them out.
* **api:** `ChaosActivationConflictException` (a `ChaosActivationException`) reports an activation refused because a scenario id is already active; the management endpoints answer it with 409 `conflict`, and the plan-file reloader retries it.
* **build:** a CycloneDX SBOM per published module (`cyclonedxDirectBom`); the agent jar's lists the ByteBuddy and Jackson it shades. Each SBOM is published with its artifact (classifier `cyclonedx`, JSON, signed with the jar when a signing key is configured). A release attests the build provenance of every published jar and the agent jar's SBOM (GitHub artifact attestations, verifiable with `gh attestation verify`); the attested files are the ones deployed, staged under `build/staging-deploy`.
* **bootstrap, startup-config:** `configFile`, `configJson`, `configBase64`, `debugDumpOnStart` and `configWatchInterval` have system properties (`-Dmacstab.chaos.configFile` and so on), read after the agent argument and before the environment, as the other settings already did; `MACSTAB_CHAOS_CONFIG_WATCH_INTERVAL` is the interval's environment variable, `MACSTAB_CHAOS_WATCH_INTERVAL` stays as its alias. The settings are resolved once at start, so a duplicated agent argument is reported once instead of once per setting; an interval that is not a number turns watching off with one `[chaos-agent]` line instead of silently; a second attach whose arguments differ from the installed agent's prints one line naming the ignored keys. `debugDumpOnStart` follows the same order (an agent argument `debugDumpOnStart=false` is no longer overridden by the environment variable).
* **bootstrap:** `ChaosPlatform.installed()` returns the installed control plane as an `Optional`, empty while no agent is installed, without throwing; the Spring session filter, the Micronaut endpoint and the Quarkus `/q/chaos` handler use it instead of catching `current()`'s `IllegalStateException` (each request without an agent built one). `ChaosPlatform` is documented as the supported entry point of `chaos-agent-bootstrap`. The Micronaut endpoint answered 503 "not installed" for any `IllegalStateException`, also one thrown by an installed control plane; that one now propagates (500).
* **api:** `ChaosDecisionRecorder.replay(scenario, sessionId)` replays the log a scenario recorded in one session; `ChaosDecisionRecorder.MAX_DECISIONS` (1,000,000) bounds each log.

### Bug Fixes

* **instrumentation:** two copies of the agent in different class loaders (two web applications that each bundle it) installing at the same time could both pass the check for another installed copy, and the later one replaced the first one's delegate: the first copy's scenarios stopped receiving calls. The check is repeated together with the install, under the bootstrap dispatcher's lock, so the later copy is refused.
* **instrumentation:** a `DatagramSocket.send` with no `DATAGRAM_SEND` scenario allocates nothing once the DATAGRAM hooks are woven: the packet's address (`getSocketAddress()`, a new `InetSocketAddress` per call) was read before the idle check, about 40 bytes per send.
* **quarkus:** `ChaosQuarkusExtension.contextPlane` and `releaseContextPlane`, public only for `ChaosArcProducer`'s reflective call across class loaders, are `@Internal` and no longer part of the recorded API.
* **opentelemetry:** the `chaos.events` counter is described as "Chaos events by type": it carries no scenario id, but its description said "by type and scenario".
* **spring, micronaut, quarkus:** a blank chaos switch value (`macstab.chaos.enabled=`) is off without a warning, as an absent one is, and as the agent arguments read it; it was warned about as an unrecognised boolean.
* **spring, quarkus:** a scenario or handle id is logged through `LogText.sanitize` (by `ChaosAutoConfiguration`, `ChaosHandleRegistry` and `ChaosQuarkusExtension`): an id with a line break wrote a second, forged log line.
* **micrometer:** the series of ended scenarios are retired when a `MeterFilter` denies the `chaos.scenarios` gauges (`management.metrics.enable.chaos.scenarios=false`): scrapes were counted by one of those gauges alone, and a denied gauge is never read, so the series of every ended scenario stayed until `close()`. Every meter read from the diagnostics now counts the scrapes.
* **testkit, spring, micronaut, quarkus, core:** the tracking control plane a test extension injects released only the scenarios a test activated: sessions opened and event listeners added through it outlived the test. `stopTracked()` closes and removes them too (a `TrackingChaosControlPlane(delegate, boolean trackListenersAndSessions)` constructor; the application's context bean keeps its listeners), and a null delegate is refused naming `delegate`. `@WithChaos` reported invalid JSON as `ConfigLoadException` instead of the documented `IllegalArgumentException` (the message keeps line and column), a failing rollback replaced the activation failure, `WithChaosSupport.close` kept only its first failure, and a plan's name and `observability` were dropped (each annotation's plan is now activated as a plan per scope). Teardown failures were swallowed without a trace in the Quarkus extension and in the control plane's release of a replaced scenario and its activation rollback; each is now a `[chaos-agent]` WARNING ([migration §41](docs/migration-2.0.md#41-a-tests-sessions-and-listeners-end-with-it)).
* **micrometer, opentelemetry:** the per-scenario series lived forever, one set per scenario id ever seen, refused activations included. Micrometer retires a scenario's series once it has ended and its last values were scraped (on the next event, or at `close()`), unless the id is still live in another scope; `chaos.activation.failures` has no `scenario` tag any more. OpenTelemetry's `chaos.events` and `chaos.activation.failures` carry no `chaos.scenario.id`; `chaos.applications`, `chaos.skips` and `chaos.injected.delay` keep it (bounded by the SDK's cardinality limit; drop it with a View).
* **bootstrap:** a `safepointStorm` with `retransformClassCount` above 0 never retransformed a class: the agent did not hand its `Instrumentation` to the runtime, so the storm made only its `System.gc()` calls, and under `-XX:+DisableExplicitGC`, where the activation is accepted for its retransforms, it produced no load at all. The agent now hands it over on every start (`-javaagent`, dynamic attach and self-attach).
* **bootstrap:** a failure without a message reported `reason=null` in the status file and `config reload failed: null` on stderr; it reports the exception's class name. A `FAILED` event of such a failure says `(no message)`, as the diagnostics record does.
* **bootstrap:** a reload failure that recurred on every tick (an id taken by a scenario activated elsewhere) rewrote the status file on every tick; it is written once, like the stderr line. An `Error` in a tick (`StackOverflowError`, `OutOfMemoryError`) ended the watching for good; it is logged and the next tick tries again. An `Error` while a reload activated its scenarios skipped the rollback after the replaced scenarios were stopped, so they were gone, the new ones were owned by nobody and every later tick reported a conflict, also after the file was fixed; the reload now rolls back on an `Error` too, and the content is not tried again until it changes (also after a transient `OutOfMemoryError` or `StackOverflowError` while it applied).
* **bootstrap:** a reloaded plan changing an id that the reloader's own scenario held until it ended, and that another activation then took, stopped and restarted the other changed scenarios on every tick before the conflict was found; every new or changed id is now checked before anything stops.
* **bootstrap:** a plan file's `observability` settings were applied after its scenarios started, so `structuredLoggingEnabled=false` still logged their first events; they are applied after the checks and before the activations, and restored when an activation fails. The startup plan's status is written before the first tick, so a tick's report is not overwritten by it.
* **core:** the diagnostics kept every activation failure since start, so a reloader or a test suite refusing scenarios grew the history (and every `snapshot()` copy of it) without bound; the 256 most recent are kept and the older ones counted in the runtime detail `droppedActivationFailures`. `debugDump()` now lists the failures, as its javadoc promised, and the JMX `debugDump` no longer claims stressor metrics. `currentSessionId` read the literal `"null"` outside a session; the key is left out then.
* **core:** a plan's observability settings (`structuredLoggingEnabled`, `jmxEnabled`) were kept by bare scenario id, so a session plan muted or hid the same id in the JVM scope and in every other session, and the last plan to apply them won; they now belong to the scenario's scope. A session closed without closing its plan handle left the settings behind; the session's close now clears them. `FAILED` events carry the `scope` attribute, so a muted plan's refusals are muted too, and the JMX `listScenarios` and `debugDump` hide a scenario by its scope.
* **api, core:** a scenario id or message with a line break split the event's log line in two, and could forge a second line; it is now escaped. Event attributes, the diagnostics' runtime details and a selector's operations iterated in an order that changed from JVM to JVM (`Map.copyOf`, `Set.copyOf`), so the same event printed, and the same plan serialised, differently between runs; attributes and runtime details now keep the order they were given in (still refusing null keys and values) and operations their declaration order. The `Snapshot` javadoc said scenarios were ordered by registration time; they are ordered by id, then scope.
* **core, instrumentation:** a `PROCESS_WAIT` was matched by the program the operating system reported for the process at wait time: a symbolic link resolved (`sh` became `dash` on Debian), and a child already reaped had no program at all, so a `commandPattern` that matched the start missed the wait. The process hooks now record the program each child was started as (the first element of the command, the name `PROCESS_START` matches) when `ProcessBuilder.start` returns, also while no scenario is active, and the wait is matched by it; a child started before the hooks were woven falls back to the reported program.
* **instrumentation:** advice for the client libraries, OkHttp, Apache HttpClient, Reactor Netty and HikariCP read its target (a Kafka subscription, a gRPC method name, a Redis command, an AWS operation, a Netty peer, a URL, a pool name) reflectively on every call, before the dispatcher found that no scenario was indexed for the operation. It now asks `BootstrapDispatcher.idle(String)` first and reads nothing while idle. A Hikari pool type without `getPoolName()` is searched once, not on every acquire, and the Netty read path finds the channel field once per class instead of on every read. The session header is decided by the session first, so a call outside any session never parses its host, and a host of four labels is an internal IPv4 address only as four plain octets of 0 to 255: `+10.0.0.1`, `10.0.0.256` or non-ASCII digits no longer receive `X-Chaos-Session`.
* **core:** the session hand-off to `ForkJoinPool` tasks, started threads and virtual threads keyed its records by `equals`: two equal tasks handed off from two sessions both ran in the second one, and a task whose `hashCode` threw failed its submission. It took a JVM-wide lock on every task run once one record was left behind by a carrier that never ran. Records are now keyed by the carrier's identity in concurrent maps, the carrier's `equals` and `hashCode` are never called, and no lock of its own is taken.
* **bootstrap, core:** with JFR or reports on, every skipped call built a `SKIPPED` event, also without a listener of the application's: the JFR sink and the reports' hit counter counted as observers, and neither reads `SKIPPED`. They are now lifecycle listeners (`@Internal ChaosRuntime.addLifecycleListener` / `removeLifecycleListener`, closed by `ChaosRuntime.close()` like every listener), which receive every event but build no `SKIPPED`. `JfrIntegration.installIfAvailable` takes the `ChaosRuntime`. The JFR `EffectApplied` event records `match` and `delayNanos`, and every chaos JFR event carries a `@Description`.
* **bootstrap, core, instrumentation:** the agent initialised `java.util.logging` during `premain` (its static JUL loggers and the platform MBean server), so an application that chooses its `LogManager` in `main` (`java.util.logging.manager`: WildFly, Quarkus in production) got the JDK's instead. The agent's classes now look their logger up when they write a line, `premain` holds the agent's log lines (256 at most, the oldest dropped and counted), and an agent thread registers the MBean and writes the held lines once the application has initialised JUL, or after 30 s. That thread is started as the agent's own work, so a startup plan's `THREAD_START` reject, with or without a name filter, never fails `premain`. A JVM that exits before then (a short-lived tool or test JVM) writes the lines still held from a shutdown hook, straight to `System.err`; before, they were lost. `THREAD_START` scenarios never evaluate the start of the agent's shutdown hooks (this one and the reports' hook): a reject still active at exit, with no name filter or on `macstab-`, made the JDK's hook loop stop at the agent's hook, so the application's later shutdown hooks never ran. Only lines at `INFO` and above are held: `FINE` lines (an `APPLIED` event per call) pushed the start's `WARNING`s out of the buffer, and each was formatted on the application's thread for up to 30 s; they are now dropped unformatted while lines are held.
* **core:** removing an asynchronous event listener (or closing the control plane) interrupted the event it was handling and silently discarded the events still queued; the event in progress now completes, the queued ones are counted in `droppedEvents`, and the removal waits for the listener at most 5 s (one WARNING after that), not at all when the listener removes itself from `onEvent`. A listener that throws on every event logged a WARNING per event; it now logs one WARNING, then FINE.
* **core:** refusals were recorded unevenly: a JVM-scoped scenario activated on a session, a refusal by `ChaosRuntime.validate` or a weaving failure of `requireHooks` (the plan-file reloader's pre-checks) and an `openSession` whose hooks could not be woven published no `FAILED` and left nothing in the diagnostics (the latter threw the raw weaving error). The scope checks now live in the validator, and each of these is recorded once (`openSession` as `ChaosInstrumentationException` under `session:<displayName>`); `validate` reports a runtime it cannot run on as `UNSUPPORTED_RUNTIME`. A plan weaves all the hooks its scenarios need (hook groups and method selectors, one call each) before it registers any, so a scenario whose hooks cannot be woven no longer lets the scenarios before it start; the reloader's pre-check weaves method selectors too, and its pre-weaves add up, so a reload whose method selector cannot be woven no longer stops and restarts the changed scenarios. A refusal the runtime cannot run is no longer retried on every tick.
* **core:** a stressor that stopped producing load kept its scenario `ACTIVE`: a stressor thread that died (an `OutOfMemoryError` in a `referenceQueueFlood` cycle, for example) disappeared without a trace, and a `gcPressure` whose `duration` or a `threadLeak` whose `lifespan` elapsed stayed `ACTIVE` with nothing running. The scenario now ends `INACTIVE` with reason `stressor failed: <type>` (the failure logged once at WARNING), `duration elapsed` or `lifespan elapsed`, with its `INACTIVE` event; the stressor's thread hands the end to the agent's expiry thread, so a concurrent `stop()` cannot deadlock with it.
* **core:** a time-bounded scenario (`activeFor`, `activeUntil`) stayed `ACTIVE` until the next matching call, so without traffic it never ended and its `INACTIVE` event never came; one agent-owned expiry thread now ends it when its bounds pass (and replaces the per-stressor expiry thread). `start()` on an `INACTIVE` scenario revived it (and built a new stressor); it is now a no-op. The time bounds were read through a skewed clock when a clock skew was applied outside any dispatch (`ChaosRuntime.adjustClockMillis`), so a day-ahead skew ended an hour-long window at once; they are read on the real clock. Re-activating an id whose window has passed publishes the old scenario's `INACTIVE` before its `STOPPED`.
* **core, instrumentation:** `ExecutorSelector.scheduledOnly` never matched (every executor call carried `periodic=false`) and `SchedulingSelector.periodicOnly` never matched a `SCHEDULE_SUBMIT`. A call on a `ScheduledThreadPoolExecutor` now counts as scheduled (the class, not `ScheduledExecutorService`, which JDK 25's `ForkJoinPool` implements too), and `scheduleAtFixedRate` / `scheduleWithFixedDelay` submit as periodic.
* **bootstrap, startup-config:** the plan poller read and digested the whole file on every tick before comparing its stamp, so an unchanged file the JVM could no longer read (`chmod 000`) failed every tick, and a modification time ahead of the clock was re-read forever; its own reads were visible to `FILE_IO` scenarios, so a `FILE_IO_READ` reject failed every reload; a same-size edit within the same second on a file system storing whole seconds was missed; and a ConfigMap `..data` link pointing at a removed directory was an error instead of a missing file. The poller now stats first and reads only a changed stamp (`StartupConfigLoader.statPlanFile`, `@Internal`), runs its file I/O as agent work, keeps a whole-second modification time provisional for one second and re-reads an unchanged stamp until a read that began after its window (`PlanFile.readStartedAt`, so a same-size edit right after a read within that second is applied too), bounds the provisional window from when a stamp is first seen, and ticks with a fixed delay.
* **bootstrap:** the plan file poller's scheduler was not the agent's own: a `SCHEDULE_TICK` suppress (`periodicOnly`) silently stopped its ticks, so editing or removing the plan file no longer switched chaos off, and a `THREAD_START` reject on `chaos-*` failed `premain` with `configWatchInterval` set. Its thread is started, and every tick runs, with the dispatch depth raised (L3).
* **bootstrap:** the management endpoints (`/actuator/chaos`, Micronaut's `/chaos`, Quarkus' `/q/chaos`) kept the handle of every plan activated through them until it was stopped there, so uniquely named, expiring plans piled up; a plan that finished on its own (spent or expired) is now closed and forgotten at the next activation, as the JMX `activatePlan` already did.
* **bootstrap:** a negative `configWatchInterval` turned watching off silently; it is reported in one line, as an unparsable value is.
* **bootstrap:** closing the reports waited for the hits writer without a limit, so a write blocked on a hanging file system held `close()` for good; it waits at most 5 s, then logs one WARNING and skips the last write. A status or staging file that cannot be removed is logged at FINE instead of being swallowed.
* **core:** re-activating the id of an expired scenario ended the expired one (its `INACTIVE` event, the listeners and the stressor's close) while the control plane's lock was held, so a concurrent activation, `addEventListener` or `close()` waited for the listeners; it now ends outside that lock.
* **core:** the agent's threads (the JVM-wide expiry thread, the stressor threads) kept the context class loader of the thread that started them, so the expiry thread kept the first activating application's loader (a dev-mode restart's) reachable for the JVM's life; they now have none. They also no longer inherit the starting thread's inheritable thread-locals (Spring's request and locale context, an MDC adapter), and on JDK 21 to 23 they are made under `doPrivileged`, so the access-control context a new thread keeps no longer holds the starting application's frames and, through their protection domains, its loader.
* **core:** a failure on the agent's expiry thread disappeared: the executor kept it in a future nobody read. A stressor whose close failed at expiry left its scenario `INACTIVE` without its `INACTIVE` event, and an expiry check that failed (a clock that throws) left the scenario `ACTIVE` for good. The close failure is now logged at WARNING and the scenario still reports `INACTIVE`; any other failure there is logged at WARNING and ends the scenario with reason `expiry failed` (a failure of that end is logged at WARNING too). `ChaosControlPlane.close()` stopped at the first scenario whose stop failed, leaving the others running and the listeners open; it now stops them all, closes the listeners and rethrows the first failure with the later ones suppressed.
* **core:** `InetAddress.getByName("")` was evaluated as a DNS lookup, although the JDK returns the loopback address without one: a `DNS_RESOLVE` reject matching every host made it throw `UnknownHostException`, and a `dnsRewrite` rewrote it. The empty name, and `getByName(null)` / `getAllByName(null)`, which the JDK answers the same way, are now skipped like an IP literal (`DNS_RESOLVE` and `DNS_ANSWER`).
* **core:** the finalizer-backlog stressor's `finalize()` slept with the dispatch depth at zero, so a user `THREAD_SLEEP` scenario matching the Finalizer thread applied to the agent's own sleeps (L3); they now run as agent work.
* **core:** on JDK 24+, a carrier-pinning stressor whose start failed partway left the threads it had started spinning: the rollback interrupts them, and their spin-wait checked only the stop flag, so each kept a carrier and a CPU busy until the JVM exited. The spin now ends on the interrupt too.
* **core:** a carrier-pinning scenario without `allowDestructiveEffects` on a virtual-thread scheduler with a single carrier (`-Djdk.virtualThreadScheduler.parallelism=1`, a one-CPU container) went `ACTIVE` and pinned nothing, with only a WARNING. It is now refused at activation with `ChaosUnsupportedFeatureException` (L17).
* **core:** the JVM-wide expiry thread, when a runtime used before the agent's install in the same JVM (a plain `new ChaosRuntime()` in a test suite that self-attaches later) started it, ran with the dispatch depth at zero for good: a `THREAD_PARK` delay applied to its parking, and a gate could hold it so no time-bounded scenario expired (L3, L19). Its depth is now raised once the agent is installed.
* **instrumentation:** a suppressed `SCHEDULE_TICK` of a one-shot `schedule(Callable)` threw the agent's own "chaos:" `CancellationException` from the task, so `get()` threw `ExecutionException` with that cause, which no real cancellation produces (ADR 0005). The task's future is now cancelled, as the JDK cancels a task it will not run: `get()` throws `CancellationException` and `isCancelled()` is `true`.
* **core, instrumentation:** log messages were built before the level check: every event, `SKIPPED` and `APPLIED` included, was formatted for a line the default level drops, and so were the stressors' `FINE` lines and the weaving failures. They are now formatted only for a line that is written. The `WARNING` for a suppressed periodic tick is the agent's own work, so a `FILE_IO` scenario on the log file no longer sees a handler's write.
* **core:** a `redirect` matching every host rewrote a Unix-domain connect too, which then failed with `UnsupportedAddressTypeException` (a Unix-domain channel cannot connect to an `InetSocketAddress`). A peer that is not an `InetSocketAddress` is no longer redirected and counts no application; an unresolved `InetSocketAddress` still is.
* **instrumentation:** a loaded class whose superclass was missing (an optional dependency absent, such as Netty's Log4j 2 logger without Log4j 2) was listed under `hookFailures` with a WARNING, although no hook was lost: the type matchers that walk the hierarchy failed to resolve the superclass. Such a class is now no target, with no failure and no WARNING; a failure while weaving a real target is still reported.
* **instrumentation:** hooks missed real funnels: a socket channel's adaptor (`channel.socket()`) connected, read and wrote without `SOCKET_CONNECT` / `SOCKET_READ` / `SOCKET_WRITE`, a server channel adaptor's accept with a timeout and `SSLServerSocket.accept()` without `SOCKET_ACCEPT` (the accept hook moves to `ServerSocket.implAccept(Socket)`), and `executeBatch()` / `executeLargeBatch()` raised no `JDBC_STATEMENT_EXECUTE`. Each is now one event per call. `AsynchronousSocketChannel` and `ForkJoinPool` submissions stay unhooked (documented).
* **micrometer, opentelemetry, core:** a delay below one millisecond was recorded nowhere: `APPLIED` carried only `delayMillis`, set from 1 ms. The event now carries `delayNanos`, and `chaos.injected.delay` is fed from it (Micrometer timer; OpenTelemetry histogram in seconds, a double, and the span attribute `chaos.delay` in seconds instead of `chaos.delay_ms`). Each Micrometer meter read from the diagnostics took its own snapshot, seven per scrape; one snapshot now serves a scrape (reused for one second). The dropped-events counter is `chaos.listener.events.dropped` in both modules, so `chaos.events` is no longer also a name prefix.
* **bootstrap, instrumentation:** a read-only `java.io.tmpdir` aborted the start ("failed to inject bootstrap bridge"), because the bootstrap bridge jar could only go there. It now goes to `/dev/shm` when the temp directory is not writable, and the error names every directory tried. The stale-jar sweep deletes only the JVM user's own jars on POSIX file systems.
* **bootstrap:** in a report directory other users can write without the sticky bit, the agent replaced and removed status and hits files another user owned. An existing report is now replaced or removed only when it is a regular file owned by the JVM's user (compared on POSIX file systems); a refused file is logged at `FINE`. `observability.md` states how the reports differ from the native library's (no `0` lines) and what a shared `reportsDir` does: one status file per directory, one hits name for every pid-1 container, values cut to 200 characters.
* **startup-config:** the directory of a Kubernetes ConfigMap mount, which holds the `..data` link an update swaps, was never checked: a plan file linked from a world-writable directory without the sticky bit loaded. It is refused now, unless the directory is on a read-only mount, as Kubernetes mounts ConfigMap volumes.
* **instrumentation, core:** with the agent in a class loader of its own (a fat jar that self-attaches), the module opens reached only the system class loader's unnamed module, so a stopped `directBufferPressure` left its memory to a later GC and the bridge could not read JDK internals. The agent opens its packages to the system class loader's unnamed module, its own module and the bridge's (the bootstrap class loader's unnamed module); the stressor logs one WARNING when the cleaner is still out of reach. The unused `java.base/jdk.internal.loader` open is gone from the manifest `Add-Opens` and the programmatic opens.
* **instrumentation:** a Netty write reject threw from `flush0()`: the write's future never completed and a channel waiting for `OP_WRITE` looped in the selector ("Unexpected exception in the selector loop"). It now fails the flushed writes with the `IOException` and closes the channel.
* **instrumentation:** on JDK 24 and later every start with the agent printed the JDK's `sun.misc.Unsafe` deprecation warning (JEP 498): ByteBuddy's agent builder initialised its Nexus, whose class injector reaches for `Unsafe`. The agent's hooks are inlined advice and need no Nexus, so the builder is created with it switched off.
* **quarkus:** the deprecated `@ChaosScenario` shorthand `executor` + `suppress` built a scenario the runtime refused (a pool worker's task run cannot be skipped); it now suppresses `EXECUTOR_SUBMIT` only. `httpClient` + `suppress` and `jdbc` + `suppress`, refused by the runtime since `suppress` on HTTP and JDBC calls is, are refused when the annotation is read, with `IllegalArgumentException` ("use delay").
* **spring, micronaut, quarkus:** the management stop answer names the stopped id `scenarioId` again, as in 1.x; earlier 2.0 builds wrote `id`.
* **quarkus:** scenarios activated through an injected `ChaosControlPlane` in a `@QuarkusChaosTest` leaked into later test classes: the bean was the untracked control plane. In test mode the producer hands out the plane `ChaosQuarkusExtension` tracks (reached through the system class loader), so they stop when the last running chaos test class ends, or when the application stops.
* **instrumentation:** a gRPC reject on a call started before the channel's name resolved panicked the channel ("Uncaught exception in the SynchronizationContext. Panic!") and left the call hanging; it now fails the call with `UNAVAILABLE`, opens no transport stream, and the channel keeps working.
* **instrumentation:** Apache HttpClient 5 `executeOpen(null, request, context)` (Spring's `HttpComponentsClientHttpRequestFactory`) was evaluated with the path only, so a `urlPattern` naming the host never matched it; HC4 `execute(host, request)` with an absolute request URI reported a doubled URL (`https://hhttps://h/v1`). Both now report the full URL, and a Reactor Netty request with a `baseUrl` and a relative `uri` reports both parts.
* **quarkus:** a Quarkus application loaded its own copies of `chaos-agent-api` and the agent, apart from the ones a `-javaagent` agent or the test extensions use, so the control plane and the installed runtime were not shared. Both extensions now declare `chaos-agent-api` and `chaos-agent-bootstrap` parent-first (`parent-first-artifacts` and `runner-parent-first-artifacts`).
* **instrumentation, packaging:** agent copies of different versions in one JVM failed obscurely ("BridgeDelegate methods without a handle slot") or mixed silently. The copy that appends the bootstrap bridge claims it with a digest of its classes, and a copy of another revision is refused before it changes anything ("a chaos agent of revision … is already installed in this JVM …; restart with one agent version"). The agent manifest carries `Implementation-Version`, and `premain` warns once, naming each jar, when a class-path copy of another version shadows the `-javaagent` jar.
* **instrumentation, packaging:** the hooks in classes of a class loader that searches its own jars before its parent (a web application with the agent jar in `WEB-INF/lib`, a child-first plugin loader) never fired: the loader defined its own `BootstrapDispatcher` from the agent jar, and the agent's delegate is installed only in the bootstrap copy. The agent jar now keeps the bootstrap bridge classes under `META-INF/macstab-chaos-bridge/`, so such a loader resolves the bootstrap copy. A loader that still sees a copy of its own (the thin `chaos-agent-instrumentation-jdk` jar bundled in an application, which is not supported) is not woven and is named in the diagnostics' `hookFailures` instead of carrying inert hooks. A second agent copy appends no second bridge jar.
* **instrumentation:** a Kafka, gRPC, Jedis, Lettuce, AWS SDK or Netty call failed with `NoClassDefFoundError` when the library was defined by a class loader that cannot see the agent's (a loader whose parent is the platform loader, as plugin and module systems build): the inlined advice named `ClientCallExtractor`, which was not on the bootstrap class path. It is now part of the bootstrap bridge, and `ArchitectureTest` checks that inlined advice names only bridge classes and holds no `invokedynamic` (illegal in Java 6 class files).
* **core:** lifecycle events are published per transition, not per call: `stop()` followed by `close()` (or a second `stop()`) published `STOPPED` twice; a scenario that ended on its own (expired, `maxApplications` spent) published nothing and now publishes `INACTIVE` with its `reason`; and a call evaluated while `STARTED` was being delivered could apply, so `APPLIED` could reach a listener before `STARTED`. The start now publishes `STARTED` before the scenario fires, and a `stop()` or expiry during that delivery stays final.
* **core:** a gate or terminal effect whose scenario has precedence `Integer.MIN_VALUE` never took effect, even when it was the only one: it was compared with a `MIN_VALUE` starting value. The first candidate now always wins, and a higher precedence (the smaller id on a tie) replaces it.
* **instrumentation:** a `corruptRead` (or `trickle`) of a channel read into a read-only `ByteBuffer` (`SocketChannel`, `DatagramChannel` and `FileChannel` reads, scattering ones included) counted as applied although the JDK refuses the read with `IllegalArgumentException`; such a read is now evaluated with a byte count of 0, so the effect neither applies nor counts. A delay still applies.
* **docs:** every effect other than a delay or a gate is an exclusive terminal (trickle, torn write and corrupted read included: they do not compose), equal precedence is decided by the smaller scenario id (it was documented as non-deterministic), and a corrupted read that reaches end of stream still counts.
* **core:** a scenario that threw while a call was evaluated (a failing clock, for example) kept the `maxApplications` reservations of the scenarios evaluated before it on that call, so they ran out early or never applied again; those reservations are now returned before the failure propagates.
* **core:** a return-value corruption of a `void` method, or of a method whose return type cannot be loaded, counted as applied (an `APPLIED` event, one of `maxApplications` used) although nothing changed; it now neither applies nor counts. `EMPTY` returned `null` for `OptionalInt`, `OptionalLong`, `OptionalDouble`, `CharSequence`, arrays and streams; it now returns their empty value (a zero-length array, `""`, an empty stream).
* **core:** `gcPressure` holds its rate over time: it was rounded to whole objects per 50 ms batch, at least one (1 KiB objects at 1,000 B/s gave 20,480 B/s), and ignored the time spent allocating. `stringInternPressure` strings shorter than 32 characters collided (a hex UUID prefix); they are now distinct. `directBufferPressure` with `registerCleaner=true` allocates and drops each buffer, as documented, instead of retaining it. A stressor `duration`, `lifespan`, `pinDuration` or `lockHoldDuration` too large for nanoseconds failed the activation with `ArithmeticException`; it now lasts until the scenario stops.
* **core:** `metaspacePressure` and `codeCachePressure` define their classes without `sun.misc.Unsafe`: on JDK 24+ they printed the Unsafe deprecation warning, and under `--sun-misc-unsafe-memory-access=deny` the metaspace stressor failed its activation and the code-cache stressor stayed active having loaded nothing.
* **core:** a suppress refused on an operation that cannot be skipped recommended `reject` even where a reject is refused too (a clock read, a worker run, a Netty read); the hint now names only effects the operation takes.
* **bootstrap:** closing the reports did not wait for the hits writer thread, so a batch it had already started could still create a staging file and rewrite the hits file after `close()` returned (and after the report directory was removed). `close()` now stops and joins the writer before the last write.
* **core:** a `FREEZE` clock skew with a future `activeFrom` froze the clock at activation, not at `activeFrom`; it now freezes the wall clock at `activeFrom` and moves the frozen `nanoTime` by the same distance. A sub-millisecond `FIXED` or `REGRESS` skew moved `Instant` reads but not `currentTimeMillis()` (or carried an `Instant` into the next millisecond): wall-clock reads are now skewed in whole milliseconds, rounded at each read, so both agree, while a sub-millisecond `DRIFT` still accumulates. A `LocalDateTime.now()` in a daylight-saving overlap was skewed from the earlier occurrence of its hour; it is skewed from the one in force. `LocalDateTime.now()` and `ZonedDateTime.now()` are returned before any conversion when no clock skew is active.
* **core:** a scenario id registered in the JVM scope and in sessions, or in several sessions, was resolved by the registry's hash order: `ChaosDiagnostics.scenario(id)` returned any scope's report, and an equal-precedence tie between them was decided arbitrarily. Both now follow the scope key: the JVM scope first, then sessions by id, on every thread.
* **core, instrumentation:** calls that never reached the real operation were evaluated: an IP literal (`127.0.0.1`, `::1`) was a `DNS_RESOLVE` / `DNS_ANSWER`, so a DNS reject broke connections to literal addresses; a Jedis connection's own set-up (`HELLO`, `CLIENT SETINFO`, `SELECT`) and a pool's validation `PING` were `REDIS_COMMAND`s, so one `set` through a validating pool counted seven; and closing a closed `Socket` again was a second `SOCKET_CLOSE`. Literals the JDK parses without a lookup are not evaluated (a hex part such as `0x7f.0.0.1` still is), the Jedis set-up and validation run in the new scope `SCOPE_REDIS_SETUP` (`ConnectionFactory` and `JedisFactory`), and a closed socket's close is skipped. A `DnsRewrite` / `DnsAnswer` scenario naming an IP literal no longer applies.
* **quarkus, micronaut, bootstrap:** `DELETE /q/chaos/a+b` stopped plan `a b`: the management path was decoded with the form rule, which reads `+` as a space. It is now percent-decoded only, so `+` is a plus and a space is `%20`; the Micronaut endpoint encodes a space as `%20` accordingly. `@QuarkusChaosTest` is `@Documented` and `@Inherited`, so a subclass of an annotated test class carries it too.
* **api, quarkus:** `skewClock(Duration.ZERO, FREEZE)` threw `IllegalArgumentException`, so the Quarkus `effect = "freeze"` shorthand froze the clock one second ahead of the activation time, and the `api.md` example failed. A zero skew is now accepted for `FREEZE` (the clock stops where it is) and still refused for `FIXED`, `DRIFT` and `REGRESS`; the shorthand passes zero. The shorthand also freezes `CLOCK_READ` (`LocalDate`, `OffsetDateTime`, `Clock.system*()`, `InstantSource.system()`), as `ChaosPresets.clockJump` does; it froze `Instant`, `LocalDateTime`, `ZonedDateTime` and `Date` only.
* **startup-config:** the plan schema's `required` lists were written by hand and wrong: a `reject` without `message`, a `delay` without its bounds and most effects' mandatory fields were accepted by the schema and refused by the agent, an empty `scenarios` was valid, and blank names passed. `required`, `minItems: 1` and the non-blank `pattern` are now probed against the mapper with samples of every type, and declared only where the agent rejects the violation in every shape (`{}` and `{"mode": "ANY"}` stay valid name patterns).
* **api:** `ChaosDecisionRecorder.replay(scenario)` merged the decisions of the JVM scope and of every session with the same scenario id, kept the decisions of earlier activations (their match numbers restart from 1), and grew without bound. It now keeps one log per scenario and scope (the event's `scope` attribute), starts a new one on each `STARTED`, replays the JVM-scoped log, and keeps at most 1,000,000 numbers per log; past that only a count grows and `replay` throws `IllegalStateException` ("decision log truncated").
* **startup-config:** a plan's parse failure named the wrong problem or none: a misspelled required field (`maxDelayy`) reported the missing field's validation error, an unknown enum value "value of the wrong type", an `int` overflow a bare `JsonMappingException`, and a null inside a value or a missing selector an "invalid value". The message now names the unknown property first, `unknown value; expected one of …` with the enum's constants, `number out of range`, `missing or null value[: <name>]`, `invalid duration` / `invalid instant` and `duplicate property`, still without quoting the input.
* **spring, quarkus, micronaut:** the test extensions claimed `ChaosSession` and `ChaosControlPlane` parameters the framework resolves itself, so JUnit failed the test with "competing ParameterResolvers": Spring's autowired test constructors and `@Autowired` / `@Value` / `@Qualifier` parameters, and every constructor parameter of a Quarkus test. The Micronaut extension resolved no `ChaosControlPlane` for a `@MicronautTest(resolveParameters = false)` class, and failed with `NoClassDefFoundError` without micronaut-test on the class path; it now resolves the parameter there and finds `@MicronautTest` by name.
* **quarkus:** with the Quarkus management interface enabled (`quarkus.management.enabled=true`), `/q/chaos` stayed on the HTTP port. It is now served by the management interface, under `quarkus.management.root-path`, and the HTTP port answers 404. The management interface authenticates on its own: secure the route with `quarkus.management.auth.*`, not only with `quarkus.http.auth.*`.
* **instrumentation:** one logical operation was evaluated several times, so delays added up and `maxApplications` ran out early: `Files.newInputStream` and the other provider opens were two `FILE_IO_OPEN` on JDK 24+ (`newByteChannel` opens through `newFileChannel`), writing or reading a list of 100 elements was 101 `OBJECT_SERIALIZE` / `OBJECT_DESERIALIZE`, `FileInputStream.readAllBytes` was one `FILE_IO_READ` per internal read, and `RandomAccessFile.readLine` one per byte on JDK 21 and none on JDK 25. No hook is applied to a bridge method.

The activation now fails with `ChaosInstrumentationException`, the failure is listed under `hookFailures`, and the next activation that needs the group weaves it again; a startup plan whose weave fails aborts `premain` like any other startup-plan failure, after writing `state=error`. An uninstall whose retransformation is refused now reports it (after removing everything else), `install` keeps its own failure when the rollback fails too, and the hook coverage (`unmatchedHooks`, `hookFailures`) starts empty after an uninstall. The classes that escape an installation are retransformed in one call, and one at a time only when that call is refused.

Reports created while the JVM shuts down fail before they register their listener or start the `macstab-chaos-hits-writer` thread.
* **bootstrap:** the hits file and the JFR `StressorSnapshot` total summed the scenarios registered at the time of writing, so the counts of stopped, expired or reloaded scenarios vanished, and the same id in two sessions gave two lines; a write that rendered before a close could also land after the final one. The counts are now cumulative per scenario id since the agent started (one line per id that applied, sorted by id), the hits file is rendered and written in one step, and the JFR total also counts applications while the `EffectApplied` event is not recorded.
* **management:** a stop that raced an activation of the same plan could answer `not-found` while the plan then ran; it now answers 409 `conflict` and the plan runs, as for any stop during an activation. A stop-all during an activation missed the plan; that activation now stops its plan once stored and answers `rejected` ("stopped by a concurrent stop-all"). The JMX bean kept the handles of plans that finished on their own (spent `maxApplications`, expired): `stopAll()` counted them and their scenarios stayed registered. * **core:** an exceptional-completion effect completed the future inside the agent's dispatch, so every dependent stage that ran inside that completion (`whenComplete`, `handle`, `exceptionally`, …) ran with all hooks off: a delay, reject or completion scenario never reached it. The future is now completed with the dispatch depth lowered, after the application is committed; the nested completion of that same future passes unevaluated.
* **core:** an `Error` while a scenario started escaped the rollback: the scenario stayed `REGISTERED` (so its id could not be activated again) and no failure was recorded. It is now rolled back, recorded as `INTERNAL_ERROR` with a `FAILED` event, and rethrown. A stressor that cannot get its resources at start (an `OutOfMemoryError`, also a thread the JVM cannot start) fails with `ChaosUnsupportedFeatureException` (`UNSUPPORTED_RUNTIME`); a thread stressor whose thread fails to start stops the threads it had started, and direct-buffer pressure that runs out of direct memory frees what it allocated. A failing `start()` of a `MANUAL` scenario is recorded the same way and leaves the scenario `REGISTERED`.
* **packaging:** relocating ByteBuddy into the agent jar also rewrote the agent's `"net.bytebuddy."` name checks, so the agent wove and sampled an application's own classes in `net.bytebuddy` packages, and `-Dnet.bytebuddy.experimental=true` never reached the relocated ByteBuddy, which reads its relocated name. Omitted fields (and explicit `null`) now take the documented defaults (`true`, `true`, 1024 bytes, one second, `true`/`true`/`false`).
* **startup-config:** plan sources disagreed on what they accept: a single scenario or an array of scenarios was read only by `@WithChaos`, which reported a failure at its position in a re-serialised copy instead of the input, and a file starting with a byte order mark failed to parse. Every source now reads plans, single scenarios and arrays through `ChaosPlanMapper.read` (bare scenarios become a plan named `default`), skips a byte order mark and reports failures at their position in the input, a syntax error with the member it is in. `{}` is read as a scenario and names the field it lacks; `null` and scalars keep their messages.
* **spring, micronaut:** a self-attach failing with a `LinkageError` (a missing attach mechanism or native library) escaped the Spring environment post-processor and the Micronaut context configurer and failed the application, and the Spring auto-configuration attached again. Both now log it and start without chaos; Spring marks the failure (`macstab.chaos.agent.attach-failed=true`) so no chaos bean is created. Micronaut and Quarkus still attach again when the `ChaosControlPlane` bean is created: inject it as `Optional` / `BeanProvider` (Micronaut) or `Instance` (Quarkus) where the application must run without the agent.
* **spring:** the startup plan (`macstab.chaos.config-file`) of a context cached across test classes stopped when the first test class using it ended, a second context with the same plan logged `SEVERE`, and a parent context applied its own plan again when a child context became ready. The plan is activated on the JVM-wide control plane, owned by the contexts that hold it (the same plan is shared and stops when the last of them closes; a different plan reusing its ids is refused with a warning), and applied only on the context's own ready event.
* **packaging:** the agent JAR shipped without the licence and notice texts it must carry: the project licence is `META-INF/LICENSE`, and `META-INF/NOTICE` merges the notices of the bundled ByteBuddy and Jackson (ASM's licence stays under `META-INF/licenses/`). Every other published JAR carries the project licence as `META-INF/LICENSE` too.
* **core:** a user scenario reached the agent's own work: a `THREAD_START` reject failed the activation of every thread stressor, a `THREAD_SLEEP` delay slowed their loops, a `FORK_JOIN_TASK_RUN` gate hung the activation of the thread-local-leak stressor forever, a `THREAD_LOCAL_SET` delay slowed its planting, and a `THREAD_LOCAL_GET` suppress in a session made the session unreadable (`NullPointerException`). Stressors are built, and their threads started, run and stopped, with the dispatch depth raised; the planting tasks and the agent's ThreadLocals are skipped by the hooks. The thread-local-leak activation fails with `ChaosUnsupportedFeatureException` when the common pool has not planted its entries within 10 s, instead of waiting forever, and empties what it planted. A stressor's `close()` from an interrupted thread now waits for its threads like any other `close()`, and keeps the interrupt.
* **core:** opening a session replaced every task submitted to a thread pool from it with a wrapper, even with no scenario in the session: a pool on a `PriorityBlockingQueue` threw `ClassCastException` (the wrapper is not `Comparable`) and `remove(task)` missed the task. A task is wrapped only once its session has a registered scenario. A `suppress` on `EXECUTOR_SUBMIT` cancels a submitted `FutureTask` and hands the pool the task itself instead of a lambda; any other suppressed runnable is still replaced by a no-op, so a priority pool that `execute`s `Comparable` runnables cannot be suppressed on `EXECUTOR_SUBMIT`.
* **core:** the `referenceQueueFlood` stressor kept every reference it enqueued: its queue was drained only on `stop()`, so the stressor itself filled the heap (a 64 MB heap ran out after about 12 s) and its thread died. It now drains the queue after each flood cycle.
* **core:** a gate with `maxApplications` never held its last admitted caller: spending the budget opened the gate before that caller reached it. The gate now holds it until `release()` or `stop()`; `release()` works on an `INACTIVE` gate scenario and opens the gate once without closing it again. Expiry still releases every waiting caller.
* **core:** a `reject` or `suppress` on `QUEUE_OFFER` dropped the tasks of every `ScheduledThreadPoolExecutor`: its delay queue answered `false`, which the pool ignores, so a scheduled task never ran (`get()` hung) and a periodic task stopped. A queue without a capacity limit is never full, so the effect no longer applies to it.
* **startup:** a plan file in a directory reached through a symbolic link was refused on Linux as world-writable (Linux reports every link as 0777); the directory's mode is now read where the link leads, and the link must be owned by the JVM's user or root, as the file must. On Windows every plan file was refused because its owner (`DOMAIN\user`) never equals `user.name`: the owner check now runs only on file systems with a POSIX view. A world-writable refusal (a mount that reports every file as 0777: Azure Files, WSL, Docker Desktop) says how to load the plan instead: restrictive mount modes, or `configJson` / `configBase64`.
* **micronaut:** `macstab.chaos.enabled` in `application.yml` (or any Micronaut config file) was ignored: only the system property and the environment variable switched chaos on, a regression from 1.0. The control-plane bean reads the application's configuration again; the endpoint switch likewise honours only local sources.
* **spring:** `macstab.chaos.enabled` and the other switches from `SPRING_APPLICATION_JSON`, a config file read from a local path (`./config/application.yml`, `spring.config.location=file:…`) or a config tree (`configtree:`, Kubernetes mounts) were rejected as untrusted, and `on` or `yes` were read as off while Spring binds them as true. Those sources are local, and the switches read `true|false|1|0|yes|no|on|off`.
* **security:** a malformed plan could put an excerpt of its input (Jackson's "Unrecognized token 'SECRET'", where the plan may hold credentials) into logs and onto stderr: `premain` rethrew the load failure with Jackson's exception as its cause, which the JVM prints, and the Spring startup applier and the management endpoints logged the exception with its cause chain. They now log only the sanitised message, and `premain` rethrows the failure without its cause. A validation message relayed into a parse failure (a duplicate scenario id), an unknown property's name and the property names of the failure's path are sanitised and capped at 200 characters. One sanitizer replaces the two that had drifted apart: C0 controls (TAB included), DEL, the C1 controls, U+2028 and U+2029 become U+FFFD, text is capped at 512 characters with a `...[truncated]` marker, and an empty message is logged as `(no message)`. The Spring applier's log lines used `_` and a silent cut at 1024 characters, and kept TAB.
* **quarkus:** `/q/chaos` read the whole request body before it checked the switch, the path and the caller, and decided the caller by `user() != null` alone: with proactive authentication an anonymous caller was served, with lazy authentication an authenticated one was refused with 401. A request is now admitted first, without reading its body: 401 unless the caller has a non-anonymous `SecurityIdentity` (a deferred one is resolved), 415 for a `POST` that is not `application/json`, 413 for a body above the 1 MiB plan cap (the connection is closed), 400 for an invalid `Content-Length`. The body of a request refused early is discarded.
* **bootstrap:** a stop of a plan that was still being activated answered 404 `not-found`, and the plan started afterwards; a second activation of that name was told a running plan had it. Both answer 409 `conflict`: an activation of the plan is in progress.
* **spring, micronaut:** the control plane of every test context stayed registered for the rest of the run, one per Micronaut test class, and what it activated was released only when the last running chaos test class ended. It is released, and what it activated stops, when its context closes.
* **core:** an activation whose hooks cannot be woven failed with an undocumented `IllegalStateException`. It fails with the new `ChaosInstrumentationException` (a `ChaosActivationException`, the weaving failure as its cause) and is recorded as `INSTRUMENTATION_FAILURE`; the management endpoints answer it as before with 422 `rejected` and log the detail. A reloaded plan whose method selector cannot be woven restores the running plan once and is not tried again until the file changes.
* **bootstrap:** a reloaded plan whose hooks could not be woven stopped and restarted the running scenarios on every poll (resetting their counters, budgets and windows) and was retried each time. Its hooks are now woven before anything changes, so the running plan stays untouched, and the same content is not tried again until the file changes.
* **instrumentation:** a suppressed `poll(timeout, unit)` returned `null` at once instead of after its timeout, as a real poll of an empty queue does: a consumer polling in a loop spun, and a thread pool's worker polled about 290,000 times in 300 ms instead of once per keep-alive. It now waits its timeout (an interrupt ends the wait with `InterruptedException`); `poll()` without a timeout still returns `null` at once.
* **bootstrap:** `jmxControl`, `reports` and the dynamic-attach opt-in accepted only `true` (and `on` for reports), while every other switch accepts `true|false|1|0|yes|no|on|off`: `jmxControl=on` or `MACSTAB_CHAOS_ALLOW_DYNAMIC_ATTACH=1` stayed off without a word. They parse like the other switches now, and an unrecognised value is reported.
* **micronaut:** `DELETE /chaos/{id}` decoded the id twice (Micronaut decodes the path variable, the shared handler decoded it again): a plan named with `%` answered 400 and one with `+` was looked up under a different name. The id is decoded once, as in Spring and Quarkus.
* **micronaut:** a `@MicronautChaosTest` with `@TestInstance(PER_CLASS)` that injected `ChaosControlPlane` failed with "chaos agent is not installed" when it was the first chaos test of its JVM: Micronaut injects such a test instance before the chaos extension installs the agent. The test control-plane bean installs the agent itself.
* **testkit:** a `ChaosSession` or `ChaosControlPlane` parameter of a static `@BeforeAll` method or of a `PER_CLASS` test constructor was injected as `null` (the session is opened per test), so the test failed later with a `NullPointerException`. It fails at injection with a `ParameterResolutionException` saying where the parameter is available, like the Spring, Micronaut and Quarkus extensions.
* **testkit:** a `@Nested` test ran without the `@WithChaos` scenarios of the classes it is nested in, so it passed without the chaos it was meant to see. The enclosing classes' scenarios are activated for it, outermost first.
* **spring:** with the application starter on the test classpath and `macstab.chaos.enabled=true`, a `@ChaosTest` context got the application starter's untracked control plane instead of the test starter's tracked one (both declare `chaosControlPlane`, and nothing ordered them), so JVM-scoped scenarios activated through the injected bean leaked into later test classes. The test configuration is ordered first.
* **bootstrap:** the agent argument `configWatchInterval=0` did not turn watching off when `MACSTAB_CHAOS_WATCH_INTERVAL` was set: only a positive argument took precedence. The argument decides whenever it is given, as documented.
* **bootstrap:** while a reloaded plan file named a scenario id that a scenario activated elsewhere held, every poll stopped the changed scenarios, failed on the conflict and started them again, resetting their counters, budgets and windows, and recorded one more activation failure. The conflict is now found before anything changes; the running scenarios keep running and the file is retried.
* **bootstrap:** the reports status file stayed at `state=error` when the config file went back to the plan already applied — a broken edit reverted, or a read that failed while a Kubernetes ConfigMap swapped its files — because unchanged content is not reloaded. It reports `state=ok` again, and the broken content, should it return, is reported again.
* **bootstrap (management):** a plan posted under the name of a running plan silently stopped that plan and took its place; every plan without `metadata.name` is named `default`, so a second unnamed plan replaced the first. It is now a 409 `conflict`; stop the running plan first. A plan that has finished is still replaced.
* **instrumentation:** a scheduled `Callable` that threw `InterruptedException` left the pool worker interrupted, even with no scenario active: the wrapper re-set the interrupt flag for the task's own exception, so completion callbacks running on the worker saw an interrupted thread. Only an interrupt from the chaos hook is restored now.
* **core:** a `rateLimit` permit was used up by a contribution that then did not take effect (an effect that does not apply to the call, a lost precedence, an exhausted `maxApplications`): with `trickle(16)` limited to one per hour, a short read the trickle could not shape took the hour's permit and the next large read was not shaped. A contribution that does not take effect now returns its permit.
* **core:** a `delay` below a millisecond was truncated to no delay while counting as applied, and every delay lost its sub-millisecond part (1.5 ms slept 1 ms). Delays are drawn and slept to the nanosecond; the `delayMillis` event attribute is unchanged.
* **core:** clock skew was applied to `Instant` and `java.time` reads in whole milliseconds: a skew below a millisecond was accepted but never moved them (only `nanoTime`), and a FREEZE kept the real sub-millisecond part, so frozen `Instant.now()` readings still moved and could run backwards within their millisecond. Wall-clock reads are skewed in nanoseconds now and a frozen instant is the same at every read; `currentTimeMillis` takes the offset floored to the millisecond.
* **core:** `errno(ETIMEDOUT)` on a socket or channel read threw `SocketTimeoutException("Read timed out")`, the exception of an expired `SO_TIMEOUT` on a socket that is still usable, so code retrying on the same socket passed the test. It is now `SocketException("Connection timed out")`, as the JDK reports a connection the kernel gave up on; `ECONNREFUSED` and `EHOSTUNREACH` on a read or write are `SocketException`s too instead of the connect-time `ConnectException` and `NoRouteToHostException`. `ChaosEffect.timeout()` remains the read timeout.
* **instrumentation:** one `DatagramSocket.send` was evaluated as two `DATAGRAM_SEND` operations, because the JDK sends it through the channel's own `send(ByteBuffer, SocketAddress)`, which is intercepted too: delays applied twice, a drop probability p dropped 1-(1-p)² of the datagrams, and counters advanced by two. It is one send again.
* **core:** closing a `threadLocalLeak` scenario submitted removal tasks to the common pool and waited for them: nothing ensured a removal reached the worker holding an entry, so the planted bytes could stay referenced, and with every worker busy `close()` blocked until they were free. Closing now releases every planted value at once from the calling thread.
* **quarkus:** a session-scoped `@ChaosScenario` on a test method was never stopped: it stayed active for the rest of the class, and a second method declaring the same id failed with an activation conflict. It now ends with its method, as a JVM-scoped one and `@WithChaos` already did.
* **spring, micronaut, quarkus:** a `@Nested` test class opened a session of its own instead of sharing its outer class's, so the outer class's session-scoped scenarios did not reach it; and when any chaos test class ended, the Spring and Micronaut extensions stopped the scenarios every class had activated through the injected `ChaosControlPlane` bean, including those of an outer class or of a class running in parallel. Nested classes now share the outer session, and bean activations are released when the last running chaos test class ends.
* **core:** a scenario, session scenario or plan activated while `close()` ran stayed registered and active on the closed control plane (its stressor and expiry threads kept running); the activation is now refused. A listener added during `close()` is refused the same way instead of being left registered.
* **core:** once the shutdown-hook interception was woven, every `Runtime.addShutdownHook` registered a wrapper thread in place of the hook, even with no scenario active: a virtual-thread hook never ran, a hook already started was accepted, and the hook's context class loader, uncaught-exception handler and priority were lost. The hook itself is registered again; a scenario still delays or rejects the registration.
* **bootstrap:** a config reload overtaken by the poller's `close()` applied nothing but still reconfigured observability, wrote an ok status and logged "config reloaded"; it now stops silently.
* **instrumentation:** a bridge injection that failed with an unchecked exception left the bridge marked as injected, so every later install failed with "failed to install bridge delegate"; a retry now injects it.
* **core:** `gcPressure` with a large rate of small objects wrapped the batch size to a negative count and allocated nothing while reporting itself running; the batch now saturates.
* **instrumentation:** a JDBC selector on a HikariCP pool name never matched a connection acquire: the hook called `getPoolName()`, which `HikariPool` does not declare, and fell back to the class name. It now reads the name from the pool's `toString()`, which HikariCP defines as the pool name. Whether a pool class declares its own `toString()` is looked up once per class, not on every acquire.
* **spring (security):** the trust check of `macstab.chaos.enabled` matched the property's exact name, while Spring resolves every relaxed spelling. An untrusted source (a config server) holding `macstab.chaos.Enabled=true` switched chaos on whenever a trusted source held `macstab.chaos.enabled`, even as `false`; a trusted source with another spelling was rejected. The winning source is now found the way Spring resolves the property, and its value and its trust are judged together.
* **startup-config:** the plan JSON `null` was read as a null plan instead of being rejected; it now fails with `ConfigLoadException`.
* **core:** `trickle` on a read no larger than its cap and `corruptRead` on a read of no bytes counted as applied without changing the call; they no longer apply there.
* **core:** `dnsRewrite` counted `InetAddress.getLocalHost()` as applied, though that lookup names no host and nothing was rewritten; it no longer applies there.
* **core:** `timeout()` on `SOCKET_CONNECT` did nothing: the plan was accepted and the scenario counted as applied, but the connect went through. It now waits out the connect timeout and throws `SocketTimeoutException("Connect timed out")`, like a peer that never answers; a connect without a timeout is left alone.
* **api:** `PathPattern` matched an empty path differently from its normal form `.`.
* **startup-config:** a plan with a syntax error inside a value (a trailing comma in the scenario list) was reported as `JsonMappingException` instead of `malformed JSON`; an unknown property's path named the property twice (`at scenarios[0].effect.delayy`), now the object that holds it, as documented.
* **instrumentation:** chaos on Apache HttpClient 4 applies; it never did, because the hook could not be woven into its Java 6 class files.
* **instrumentation:** a class first loaded while a hook group was being woven (the object streams, the socket classes) escaped the hooks of the groups woven before it; it is now woven too.
* **instrumentation:** a torn socket stream write now really resets the connection (`SO_LINGER` 0, then close) after sending its prefix; before, the socket stayed open, so the peer saw neither a reset nor an end of stream and the writer could keep writing.
* **core:** `randomSeed` now also fixes the effects' own random choices: the torn-write length, the bit `corruptRead()` flips and the `SHUFFLE` order of a DNS answer, each derived from the match's seed. They were drawn from `ThreadLocalRandom`, so a seeded run could not reproduce them.
* **reload:** a plan file changed between the agent's startup read and the reloader's start was never applied (the baseline came from a second read; the loader now hands its read to the reloader). A transient activation failure (an id taken elsewhere, a weaving failure) is retried instead of being skipped until the file changes. A ConfigMap swap during a read no longer reports a spurious error. A file missing for a single tick no longer stops and restarts every scenario. A plan file or ConfigMap link owned by another user (root excepted) is refused, so another local user cannot plant one in a shared directory such as `/tmp`.
* **quarkus:** the `/q/chaos` route moved into its own extension, `chaos-agent-quarkus-management` (+ `-deployment`); the main extension no longer pulls in `quarkus-vertx-http` (which started an HTTP server in command-mode applications). The route now always answers (503 without the agent instead of hanging), works off the event loop, uses a body another extension already read, URL-decodes ids, answers 404 outside its root instead of stopping everything, reads `macstab.chaos.management.enabled` at runtime, and stops its plans on shutdown and dev-mode reload.
* **micronaut:** the `/chaos` endpoint answers with the operation's status code (it always answered 200) and no longer installs the agent when it is enabled; 503 when no agent is installed.
* **management:** precise outcomes and codes in `ChaosManagement`: `invalid` 400, `conflict` and `unmanaged` 409, `rejected` 422, `not-found` 404.
* **sessions:** a pool worker created by a submission inside a session (a `ThreadPoolExecutor` or Tomcat worker, every fork-join worker) inherited the session for life and ran later, unrelated tasks in it; pool workers now inherit none — tasks keep carrying their submitter's session. A thread that was started in a session but never ran no longer slows down every later fork-join task.
* **sessions:** `ChaosSessionFilter` now lets the header decide every request: without `X-Chaos-Session` a request runs outside any session. The JDK HTTP clients send the header to internal hosts only; the agent setting `sessionHeaderHosts` adds globs (`*` for all). A request the builder cannot copy is sent unchanged.
* **core:** a session-scoped scenario activated outside a session (through the plan-file reloader or JMX) was registered JVM-wide and fired for every thread; it is now refused.
* **core:** `activate(ChaosPlan)` validates every scenario and checks every id before starting any; an invalid later scenario used to roll back earlier ones that had already injected faults.
* **core:** a plan's observability settings belong to that plan: a rejected plan with the same ids, a re-posted plan or a second `close()` no longer strip the settings of the running plan. Plan handles close idempotently.
* **jmx:** `activatePlan` activates the plan as one unit (validated first, observability applied, rolled back together); `stopScenario` stops the scenario's plan.
* **micrometer:** a binder bound to several registries removed only the last listener on `close()`.
* **bootstrap:** self-attached installs (the framework starters, `installLocally`) ignored every `MACSTAB_CHAOS_*` environment variable.
* **testkit:** `@WithChaos` told plans from scenarios by the substring `"scenarios"`; it now reads the JSON's structure (plan, scenario or array of scenarios; `ChaosPlanMapper.readPlanOrScenarios`).
* **api:** `Errno.code()` is the current operating system's number (`EAGAIN` is 35 on macOS); `linuxCode()` keeps the Linux value. `ETIMEDOUT` on a write no longer reports "Read timed out"; an injected `ENOENT` on `Files.deleteIfExists` returns `false` as the real method does.
* **api:** `replayMatches` inside the warm-up is rejected; `ChaosDecisionRecorder.matches(id, sessionId)` keeps sessions apart.
* **instrumentation:** clock call sites in interfaces (default and static methods, lambdas) are rewritten too; a `SYSTEM_CLOCK_*` scenario without `clockCallSites` logs a warning.
* **instrumentation:** a URL filter (`urlPattern`) never matched the JDK `HttpClient`: the URL was read reflectively through the request's internal class, which is not open to the agent, and came out `null`. The advice, inlined into `HttpClientImpl`, now calls `HttpRequest.uri()` directly.
* **startup-config:** a reloaded plan with an invalid scenario stopped the changed scenarios, activated part of the new plan and then rolled back, so for a moment neither plan was fully active and part of the invalid one was. Every new or changed scenario is now validated before the active set is touched.
* **micrometer:** `chaos.events` was registered with different tag keys per event type (`reason` on skipped, `category` on failed), which Prometheus registries reject; those tags moved to `chaos.skips` and `chaos.activation.failures`, so every meter has one tag key set.

### Deprecations

* **api:** `ChaosMetricsSink` is deprecated for removal, and with it the `chaos.effect.applied` metric: a second metrics API beside the events, for the count `chaos-agent-micrometer` and `chaos-agent-opentelemetry` publish as `chaos.applications`. Its javadoc no longer names `chaos.gate.block.duration`, which nothing produced. The `APPLIED` event attribute `delayMillis` is deprecated in favour of `delayNanos`; it is still set from 1 ms.

### Performance Improvements

* **core:** `ScenarioRegistry` keeps an immutable index from operation type to controllers, pre-sorted by descending precedence then id and swapped on register/unregister. `match()` evaluates only the scenarios whose selector names the intercepted operation and no longer sorts per call; clock-skew reads use the same index and return immediately when no scenario names the clock.
* **core:** an intercepted call with no scenario for its operation allocates nothing and costs 7–12 ns, on every hooked operation; it built a context and a decision first (23–54 ns and 104–200 B), and whether the JIT removed the allocation varied between runs.
* **api:** `NamePattern` GLOB matching uses an allocation-free wildcard matcher instead of a compiled regex.


### Documentation

* **api:** `ChaosUnsupportedFeatureException` is documented with the cases that throw it (heap or direct-memory pressure above the limit, a stressor without its resources, a thread-local leak the common pool did not plant); the docs named a missing JFR and virtual threads on JDK 17, which no supported runtime throws for.
* **benchmarks:** the "exhausted scenario" benchmarks of `ChaosRuntimeBenchmark` and `HttpClientBenchmark` spend their one-shot scenario in setup and check that it is INACTIVE, `tenScenarios_oneMatch` puts its nine extra scenarios on the benchmarked operation (with a pattern that does not match) instead of on another one, and the HTTP benchmarks send a URL held in a `@State` field rather than a constant the JIT folds. The published figures (`benchmarks.md`, the README, the user guide, the configuration reference) were measured with scenarios that never exhausted and before the operation index; they are replaced by a JDK 25 run. `sessionIdMiss` opens its session on a thread of its own: opening a session binds the opening thread, so the benchmark thread was inside the session and measured an applied zero delay (about 310 ns); a call outside the session costs about 15 ns over `zeroScenarios`, within its target.
* **examples:** the examples assert that chaos applied: `ActuatorLiveChaosIT` charges through a WireMock gateway on a free port, activates its plan through `POST /actuator/chaos`, asserts the scenario's applied count and stops it through `DELETE`; `RetryResilienceTest` asserts two rejected connects; `VirtualThreadPinningIT` asserts the pinning scenario is ACTIVE before and after the burst; `SlaValidationTest` asserts the delay applied. Their READMEs describe the code as it is.
* **core:** what a `suppress` on an executor does to the caller: a `ThreadPoolExecutor.submit` future is cancelled, a plain `execute` task is dropped, a `ScheduledThreadPoolExecutor` one-shot future completes with `null` (the task is replaced before the future is built, so it is never cancelled), and the virtual-thread-per-task executor raises neither submit operation. Linux and macOS are the supported operating systems (Windows best effort, untested), and a path pattern is matched case-sensitively, also on a case-insensitive file system.
* **api:** the 4096-character cap on a name pattern was described as a ReDoS defence; it bounds compilation, not matching. The docs now say that a REGEX runs with Java's backtracking engine on the intercepted thread without a time limit, so plans with REGEX patterns must come from trusted authors.
* **bootstrap, testkit:** self-attach needs no JVM flag: the docs no longer ask for `-Djdk.attach.allowAttachSelf=true` or claim that the test extensions set it (none does; ByteBuddy attaches from a helper process when self-attach is not allowed). They describe the JEP 451 warning a self-attach prints on JDK 21+ and how to avoid it (`-javaagent:` or `-XX:+EnableDynamicAgentLoading`), and that an executable jar's `Launcher-Agent-Class` goes through `agentmain` and so needs `MACSTAB_CHAOS_ALLOW_DYNAMIC_ATTACH`. A child-JVM test installs and applies chaos without either flag.

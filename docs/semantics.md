# Evaluation Semantics

> The rules the agent follows when an intercepted call meets the active scenarios, stated as laws. Every law here is enforced by code and covered by tests; where a law names a class, that class is where it is enforced.

---

## 1. Identity

**L1 — No scenario, no change.** With no active scenario and no open session the agent weaves no JDK class (hooks are woven per hook group on the first activation that needs them, `JdkInstrumentationInstaller.HookGroup`; `openSession` weaves the six groups that carry a session to other threads and services: `THREAD_START`, `THREAD_POOL_EXECUTOR`, `EXECUTOR_SUBMIT`, `SCHEDULED_EXECUTOR`, `FORK_JOIN` and `HTTP_CLIENT`) and alters no call. A session without scenarios alters no call either: a task submitted to a pool from it reaches the pool unchanged, and is wrapped to carry the session only once the session has a registered scenario. With `instrumentation=eager` the hooks are woven at start, and each intercepted call returns its unmodified result after one index lookup.

**L2 — An empty plan is no plan.** A plan whose scenarios all fail to match behaves exactly like no plan for every call they do not match. Woven hook groups stay woven until the agent is uninstalled, but a woven hook with no matching scenario returns the call unmodified. Method hooks (`METHODS`) are the exception: removing the last method scenario restores the original bytecode.

**L3 — The agent never evaluates itself.** Calls made by the agent's own code are never matched: the reentrancy depth is raised while they run (`BootstrapDispatcher`). That covers evaluation, reflective URL extraction, expiry threads (also one a runtime used before the agent's install started: its depth is raised once the agent is installed), the weaving (every transformation of the agent's transformers, also of a class an application thread loads, and the installs, retransformations and resets of hook groups and method hooks: ByteBuddy's own reflection is no `REFLECTION_INVOKE` target, so a reflection reject cannot leave a hook missing; the same for the reflective read of the gRPC hook's failures in `hookFailures`), and stressors with their set-up and teardown: a stressor is built and closed with the depth raised (so a `REFLECTION_INVOKE` reject never keeps the direct-buffer stressor's buffers after its stop), and its threads are started, run and stopped with it raised, so a user `THREAD_START` reject or `THREAD_SLEEP` delay never reaches them; the finalizer-backlog stressor's `finalize()` sleeps on the JVM's Finalizer thread with it raised too. The threads `premain` starts (the deferred logging start, the reports writer, the plan file poller) are started the same way, so a startup plan's `THREAD_START` reject never fails the agent's start, and `premain`'s own read of the `java.util.logging` state (a `Method.invoke`) runs with the depth raised, so a startup plan's `REFLECTION_INVOKE` scenario neither counts it nor delays the deferred start; the agent's shutdown hooks (the release of the held log lines, the reports' last write), which the JDK starts with the depth at zero, are skipped by `THREAD_START` (`AgentHookThread`), so a reject still active at exit never aborts the JDK's hook loop, and the application's own hooks still run; the poller's ticks run with the depth raised too, so a `SCHEDULE_TICK` scenario never stops its reloads. The thread-local-leak stressor's planting tasks on the common pool are skipped by `FORK_JOIN_TASK_RUN` and plant with the depth raised (the planted ThreadLocals themselves are plain ones: they are the leak). The agent's own ThreadLocals (the session stack, the corruption seed) are skipped by `THREAD_LOCAL_GET` / `THREAD_LOCAL_SET`, so a ThreadLocal scenario never hides the current session. The agent's own MBeans (the `com.macstab.chaos.jvm` domain) are never a `JMX_INVOKE` / `JMX_GET_ATTR` target. The agent's event delivery is its own work too, on whichever thread publishes: writing a log line (the built-in event log, the agent's WARNINGs, the held lines' release), handing an event to an asynchronous listener's queue, and a plan's `debugDumpOnStart` print run with the depth raised, so a `FILE_IO_WRITE` or `QUEUE_OFFER` scenario neither counts, delays nor rejects them; a listener the user registers synchronously is called at the publisher's depth. One exception lowers the depth inside a dispatch: an exceptional-completion effect completes the future with the depth lowered, after its application is committed, so the dependent stages that run inside that completion (`whenComplete`, `handle`, `exceptionally`, …) are evaluated like any other call; only the nested completion of that same future passes unevaluated.

**L3a — The JDK's own use of a general primitive is not a target.** This is an enumerated list, not a general rule: a JDK use that is not listed here stays reachable (a JDK `ReentrantLock`, a plain JDK `ThreadLocal`, JMX introspection, `LockSupport.park` inside the JDK). Listed:
- **Class loading** (`ClassLoader.loadClass(String[, boolean])`, scope-only `SCOPE_JDK_INTERNAL`, woven with any `FILE_IO_*` or `ZIP_*` scenario): the class files and archives a loader reads are not `FILE_IO_*` or `ZIP_*` targets. A loader that overrides `loadClass(String)` itself (Tomcat's `WebappClassLoaderBase`) bypasses the bracket. A `ZIP_INFLATE` scenario still cannot be narrowed by subject (a `ZipFile` / `JarFile` read outside class loading is evaluated).
- **Temporary direct buffers** (`sun.nio.ch.Util.getTemporaryDirectBuffer` / `getTemporaryAlignedDirectBuffer`, which allocate through `allocateDirect` on JDK 21): not `DIRECT_BUFFER_ALLOCATE` targets.
- **The JDK's own collection requests** (`java.nio.Bits.reserveMemory`, `FileChannelImpl.mapInternal` behind `map`): not `SYSTEM_GC_REQUEST` targets, so direct memory and mappings are still reclaimed under a GC-request suppress.
- **The `CompletableFuture` timers** of `orTimeout` / `completeOnTimeout`: on JDK 21 their submission (`CompletableFuture$Delayer.delay` of a `$Timeout` or `$DelayedCompleter`) is not a `SCHEDULE_SUBMIT` target and their tick is not a `SCHEDULE_TICK` target; on JDK 25 the `DelayScheduler$ScheduledForkJoinTask` that runs a `$Timeout` is not a `FORK_JOIN_TASK_RUN` target; on both the first completion a timer makes (`$Timeout.run`, `$DelayedCompleter.run`) is not an `ASYNC_COMPLETE*` target (the one-shot `SCOPE_JDK_COMPLETION` marker, cleared when the timer's `run` returns). `CompletableFuture.delayedExecutor` is the application's scheduling and stays evaluated. Documented, not changed: on JDK 21 `EXECUTOR_WORKER_RUN` still fires on the `CompletableFutureDelayScheduler` worker; on JDK 25 `delayedExecutor` tasks run on the pool's `DelayScheduler` thread, so a `FORK_JOIN_TASK_RUN` delay on them delays every `CompletableFuture` timer of that pool.
- **The random devices** `/dev/random` and `/dev/urandom` (`SecureRandom`, `UUID.randomUUID`): not `FILE_IO_*` targets of a selector without a path pattern; a path pattern that matches them reaches them.
- **The JDK `HttpClient`'s selector thread** (`HttpClientImpl$SelectorManager`): its `select` is not a `NIO_SELECTOR_SELECT` target.
- **JDK-internal futures** (`jdk.internal.*`, such as the `HttpClient`'s): not `ASYNC_*` targets; an `AsyncSelector` cannot name a future's class yet. The context of a completion or cancel now names the future's class.
- **JDK-private `ThreadLocal` classes**, for a `ThreadLocalSelector` with the `ANY` pattern only: `Exchanger$Participant`, `ReentrantReadWriteLock$Sync$ThreadLocalHoldCounter`, `jdk.internal.foreign.BufferStack$1`, `jdk.internal.jimage.ImageBufferCache$1`, `jdk.internal.math.FloatingDecimal$1`, `jdk.internal.misc.CarrierThreadLocal`, `jdk.internal.misc.TerminatingThreadLocal` (and `$1`), `sun.net.www.protocol.http.NegotiateAuthentication$1`, `sun.nio.ch.Invoker$1`, `sun.nio.ch.IOVecWrapper$1`, `sun.nio.ch.Util$1`, `sun.nio.fs.NativeBuffers$1`. Never `ThreadLocal`, `InheritableThreadLocal` or `ThreadLocal$SuppliedThreadLocal` (`ThreadLocal.withInitial`): the application creates those.
- **Serialization hooks**: the object streams' reflective calls of a class's `writeObject(ObjectOutputStream)`, `readObject(ObjectInputStream)`, `readObjectNoData()`, `writeReplace()` and `readResolve()` (by name and descriptor) are not `REFLECTION_INVOKE` targets.
- **The JDK's own reflection**: a `Method.invoke` whose caller (the frame below `Method.invoke`) is a JDK class, one of a named module of the bootstrap or platform class loader, is not a `REFLECTION_INVOKE` target: `EnumSet` reading an enum's constants (also an application enum's), the TLS provider's set-up behind `SSLContext` and an OkHttp client. A `jvmRuntime` selector cannot narrow reflection by caller, so this holds for every `REFLECTION_INVOKE` scenario. The caller is found by a stack walk, made only for a call whose session and selector a scenario matches. A JDK API that reflects through a class of its own loader (the `sun.reflect.misc` trampoline behind `java.beans` and standard MBeans) stays a target, and so does a class the application appends to the boot class path (`-Xbootclasspath/a`, `Instrumentation.appendToBootstrapClassLoaderSearch`), which is in the boot loader's unnamed module.
- **Thread pool worker locks**: `ThreadPoolExecutor$Worker` is not a `MONITOR_ENTER` target of a `MonitorSelector` with the `ANY` pattern.
- **A JDBC driver's or pool's own statements** (scope-only `SCOPE_JDBC_INTERNAL`): `Connection.isValid(int)` of every driver (pgjdbc runs a statement there), and HikariCP's validation (`PoolBase.isConnectionDead`), connection set-up (`newPoolEntry`: `connectionInitSql`, `connectionTestQuery` and its driver checks), reset (`resetConnectionState`) and the rollback of a connection taken back dirty (`ProxyConnection.close`). The statements, prepares, commits and rollbacks inside them are not `JDBC_*` targets: a reject never makes the pool evict its connections or time out a borrow, and they spend no `maxApplications`. Another pool's validation query (DBCP2, tomcat-jdbc, c3p0) stays a target.
- **The close an interrupt makes**: the JDK closes the interruptible channel a thread is blocked on from inside `Thread.interrupt()`, on the interrupting thread and under the channel's `closeLock` (on JDK 21 also the target's `interruptLock`), and swallows any failure. That close is not a `FILE_IO_CLOSE` or `SOCKET_CLOSE` target: a delay or gate there would block `interrupt()` itself (`ExecutorService.shutdownNow()`) and the interrupted thread, and the scenario would see the interrupter's session. Found by a short stack walk, made only for a close a scenario may select.
- **The virtual-thread scheduler's carriers** (`jdk.internal.misc.CarrierThread`): a fork-join task run on a carrier (a virtual thread's start or wake-up) is not a `FORK_JOIN_TASK_RUN` target.

**L4 — One logical call, one evaluation.** When a hooked method reaches another hooked method for the same operation (`getByName` → `getAllByName`, a pool proxy → the driver statement, an overload → its delegate, `Files.newInputStream` → the provider's `newByteChannel` → `newFileChannel` on JDK 24+, `writeObject` of a list → the `writeObject` of each element, `FileInputStream.readAllBytes` / `readNBytes(int)` and `RandomAccessFile.readLine` → the stream's own reads), only the outermost call is evaluated (call-depth scopes, `BootstrapDispatcher.enterScope`). Delays do not add up across the nesting, the probability is drawn once and `maxApplications` is spent once. Bridge methods are never hooked: a call through a bridge is the one call of the method it bridges to. Still evaluated once per inner read (documented, not merged): `FileInputStream.transferTo` to a stream that is not a file, `RandomAccessFile.readUTF`, and `readNBytes(byte[], int, int)` inherited from `InputStream`.

## 2. Matching one scenario

A scenario matches a call when its selector matches the call's context. Every field of a selector is a conjunct:

**L5 — Filters are conjunctive.** The operation must be in `operations`, and every non-null filter must hold (`SelectorMatcher`).

**L6 — Unknown never matches.** A filter on a value the call does not carry is not satisfied: an unresolved peer never lies in a `remoteCidr`, a stream without a path never matches a `pathPattern`, an operation without a byte count never satisfies `minBytes`/`maxBytes`. Selectors that combine such a filter with an operation that can never carry the value are rejected at construction or activation (a size filter with `SOCKET_CONNECT`, a peer filter with `SOCKET_ACCEPT`).

## 3. The policy of one scenario

For a matching call, the scenario's `ActivationPolicy` is checked in this order; the first failing step ends the evaluation (`ScenarioController.evaluate`):

| Step | Check                                                     | On failure                                           | Counted as a match? |
|------|-----------------------------------------------------------|------------------------------------------------------|---------------------|
| 1    | The scenario is started (`ACTIVE`)                        | skip                                                 | no                  |
| 2    | The call's session equals the scenario's session, if any  | skip                                                 | no                  |
| 3    | The selector matches (§2)                                 | skip                                                 | no                  |
| 4    | Now is before `activeUntil` and within `activeFor` (the real clock, never a skewed one) | the scenario becomes `INACTIVE` (`"expired"`); without calls the agent's expiry thread ends it when the bounds pass | no                  |
| 5    | Now is at or after `activeFrom`                           | skip                                                 | no                  |
| 6    | More than `activateAfterMatches` matches have been seen   | skip                                                 | yes                 |
| 7    | The probability draw succeeds                             | skip                                                 | yes                 |
| 8    | A rate-limit permit is available                          | skip                                                 | yes                 |
| 9    | An application fits under `maxApplications` (reserved)    | skip                                                 | yes                 |

**L7 — Time bounds use the real clock.** `activeFrom`, `activeUntil` and `activeFor` are read from the system clock inside the dispatch, where the agent's own clock hooks return the real value: a clock skew the agent injects cannot move them.

**L8 — The probability is in (0, 1].** `0.0` is rejected; a scenario that must never fire is not activated. `1.0` always passes step 7.

**L9 — Draws are reproducible.** With a fixed `randomSeed`, the probability draw and the sampled delay of the *n*-th match are fixed: both derive from a `SplittableRandom` seeded with `seed ^ rotl(n, 32) ^ (id.hashCode() * 0x9e3779b97f4a7c15L)` (the match number rotated by 32 bits, the id's hash spread by the 64-bit golden-ratio constant), the delay from an independent split stream, so they are not correlated. So are the effects' own choices of that match: the length of a torn write, the bit a corrupted read flips and the order of a shuffled DNS answer each derive from the same seed, salted per kind of choice.

**L9a — A replay log replaces the draw.** With `replayMatches`, step 7 passes exactly on the listed match numbers (counted from 1 over every match since the scenario started, warm-up included, as step 6 counts them). `ChaosDecisionRecorder` records the numbers from the `match` attribute of `APPLIED` events, so a run — seeded or not — replays decision by decision as long as the calls arrive in the same order. An empty list is accepted and never passes step 7: such a scenario matches and counts its matches but never fires. Its log is per scenario and scope (the event's `scope` attribute: `jvm` or `session:<id>`), restarts with each `STARTED` of that scenario in that scope, and holds at most 1,000,000 numbers; a truncated log is not replayed.

**L10 — A rate-limit window starts at activation.** Windows are fixed, anchored at the scenario's start (not at an epoch boundary); a clock that steps back re-anchors the window.

## 4. Composing several scenarios

All scenarios that pass §3 for a call contribute. They are ordered by descending `precedence`, then ascending scenario id, then scope key (`ScenarioRegistry`): the same id in the JVM scope (`"jvm"`) comes before its sessions (`"session:<id>"`), and sessions by id, so an equal-precedence tie between scopes is decided the same way on every thread. The same order answers `ChaosDiagnostics.scenario(id)` for an id registered in several scopes: the JVM scope's report, else the session with the smallest id.

**L11 — Delays add up.** The delays of every contribution are summed and applied first. A single delay is at most 720 hours, so the sum stays far from overflow (it saturates at `Long.MAX_VALUE` ms regardless).

**L12 — One gate.** Of the gate contributions, the one with the highest precedence (the smallest scenario id on a tie) holds the caller, after the delay; a sole gate holds it whatever its precedence, `Integer.MIN_VALUE` included. Expiry (`activeFor`, `activeUntil`) releases every caller held at the gate; a spent `maxApplications` does not, so its last admitted caller is held like the others until `release()` or `stop()`. A `release()` of an `INACTIVE` scenario opens the gate once without closing it again.

**L13 — One terminal.** Every effect other than a delay or a gate is a terminal: reject, suppress, an errno, exception injection, exceptional completion, return-value corruption, timeout, connection reset, redirect, a DNS answer or rewrite, a spurious wakeup, and the data-shaping effects trickle, torn write and corrupted read. They are exclusive and do not compose: of the terminal contributions, the one with the highest precedence (the smallest scenario id on a tie) decides the outcome, after the delay and the gate, so a trickle and a corrupted read on the same read never both apply. A sole terminal decides whatever its precedence, `Integer.MIN_VALUE` included.

**L14 — Only what takes effect counts.** `APPLIED` is published, `appliedCount` grows and `maxApplications` is spent only for contributions that take effect: every delay, the winning gate and the winning terminal. A scenario that matched but lost on precedence keeps its budget (`ScenarioContribution.commit`/`release`). An effect that cannot change the call in hand does not take effect either, and counts nothing: a timeout on a call without one, a torn write of fewer than two bytes or to a file stream, a trickle on a read no larger than its cap, a corrupted read of no bytes or of a kernel transfer, a trickle or corrupted read of a channel read into a read-only `ByteBuffer` (the JDK refuses such a read with `IllegalArgumentException`, so it is evaluated as a read of no bytes: byte count 0; a delay still applies), a DNS rewrite of the local-host lookup, a reject or suppress of `QUEUE_OFFER` on a queue without a capacity limit (`remainingCapacity()` is `Integer.MAX_VALUE`, or no less than `Integer.MAX_VALUE - size()`: an unbounded `LinkedBlockingQueue`, a `PriorityBlockingQueue`, a scheduled pool's delay queue), which is never full. Delays and gates on such an offer still apply. Every effect the validator accepts on an operation changes that operation's call when it counts (`EffectReachesTheCallTest`); a DNS shuffle that happens to keep the order is one of its draws and counts. A corrupted read is decided before the read runs, so one that ends up at end of stream (no bytes returned) counts although no bit is flipped.

**L15 — An interrupted gate restores the interrupt.** An interrupt ends the gate wait; the interrupt flag is restored and the call proceeds, so the intercepted method observes the interrupt as it would without chaos.

## 5. Clock skew and stressors

**L16 — A clock skew applies to every clock read while its time bounds hold.** It honours `activeFor`, `activeFrom` and `activeUntil` and is session-scoped when its scenario is. It is not a per-call application, so `maxApplications`, `rateLimit`, `activateAfterMatches` and `probability < 1.0` are rejected for it. `FREEZE` freezes at the moment the scenario becomes active (`activeFrom` when it is later than the activation), the wall clock and `nanoTime` together. Wall-clock reads are skewed in whole milliseconds, rounded at each read, so millisecond and `Instant` reads agree; `nanoTime` to the nanosecond. Without a clock-skew scenario a `java.time` read is returned before any conversion.

**L17 — A stressor runs from activation until it ends.** It ends on `stop()`/`close()`, when `activeFor` elapses or at `activeUntil`. `activeFrom`, `maxApplications`, `rateLimit`, `activateAfterMatches`, `probability < 1.0` and `replayMatches` are rejected for it. Its parameters are never reduced silently: heap pressure, a thread-local leak's planted values or a reference-queue flood's cycle above the free heap (refused before anything is allocated), a thread-local leak whose entries overflow an `int`, more interned strings than their length makes distinct or than the caps, and an interval below 1 ms are refused at activation; a duration too large for nanoseconds lasts until the stressor ends, and one below a millisecond (a `finalizerDelay`, a deadlock's `acquisitionDelay`) is kept, not truncated to none. A stressor that this JVM's flags leave without any load is refused at activation (`ChaosUnsupportedFeatureException`): a `safepointStorm` with `retransformClassCount = 0` under `-XX:+DisableExplicitGC`, a `finalizerBacklog` under `--finalization=disabled`, and a `virtualThreadCarrierPinning` without `allowDestructiveEffects` on a scheduler with a single carrier (`-Djdk.virtualThreadScheduler.parallelism=1`, a one-CPU container), which must leave that carrier free (L18); the flags are read at the first such activation, never at agent start. A stressor that stops producing load on its own ends its scenario `INACTIVE` with a reason, as an expiry does: its thread failed (`stressor failed: <type>`, logged once at WARNING), something other than its stop interrupted one of its threads (`stressor interrupted: <type>`: a `ThreadGroup.interrupt()`, a container's thread clean-up), its `duration` elapsed (`duration elapsed`, `gcPressure`) or its `lifespan` elapsed (`lifespan elapsed`, `threadLeak`).

**L18 — Unrecoverable states need consent.** Deadlocks, leaked non-daemon threads and holding every virtual-thread carrier (which stops every virtual thread in the JVM) require `allowDestructiveEffects`. Without it, a carrier-pinning stressor leaves one carrier free, and is refused on a single-carrier scheduler (L17).

## 6. Lifecycle

**L19 — Stop is final for a handle.** A stopped or expired scenario never fires again; `start()` on it is a no-op (it builds no stressor and publishes nothing): only a `REGISTERED` scenario starts. The state follows the time bounds: a scenario with `activeFor` or `activeUntil` becomes `INACTIVE` when they pass, also without any call — one agent-owned expiry thread checks each time-bounded scenario at its end, rechecks later when the scenario's clock is behind, and is cancelled on stop — and `state()`, the diagnostics and a re-activation of the id see the transition first. The bounds are read on the real clock, never through a clock skew, also from a caller outside any dispatch (`ChaosRuntime.adjustClockMillis`). A call decided before `stop()` returned completes. Each lifecycle transition publishes one event, from the thread that made it: `STARTED` on `REGISTERED → ACTIVE`; `INACTIVE` on `ACTIVE → INACTIVE`, when the scenario ends on its own, with `reason` `expired` (`activeFor`, `activeUntil`), `max applications reached` (from the thread whose `APPLIED` spent the budget, after it), or a stressor's own end (`stressor failed: <type>`, `stressor interrupted: <type>`, `duration elapsed`, `lifespan elapsed`, L17; the expiry thread makes that transition too); `STOPPED` on every transition into `STOPPED` (from `REGISTERED`, `ACTIVE` or `INACTIVE`), so a second `stop()` or a `close()` after `stop()` publishes nothing. A stop racing an expiry yields `STOPPED` alone or `INACTIVE` and `STOPPED`, never two of the same; they come from different threads, so a listener may receive them in either order. `STARTED` is published before the scenario fires: a call made while `STARTED` is being delivered is neither matched nor applied (the diagnostics already report `ACTIVE`), and a `stop()` or an expiry during that delivery is final.

**L20 — A finished scenario can be replaced.** Activating an id whose scenario is `STOPPED` or `INACTIVE` replaces it atomically; activating an id whose scenario is still `REGISTERED` or `ACTIVE` throws `ChaosActivationException` and changes nothing.

**L21 — A failed activation leaves no trace.** If validation or weaving fails, or the stressor of a scenario that starts at activation cannot start (it is built before the scenario is registered), the scenario is not registered, a finished scenario of the same id stays as it was, the only event published for its id is `FAILED`, and the failure is recorded in diagnostics and on that event with its category (`INVALID_CONFIGURATION`, `UNSUPPORTED_RUNTIME`, `ACTIVATION_CONFLICT`, `INSTRUMENTATION_FAILURE`, or `INTERNAL_ERROR` for an `Error` such as a `LinkageError` from a stressor or a listener). Every refusal and weaving failure is recorded once, wherever it happens: an activation, a session's activation (also of a scenario whose scope does not fit), `ChaosRuntime.validate` and `requireHooks` (the plan-file reloader's pre-checks), a plan's validation, and a session's own weaving (recorded under `session:<displayName>`). A plan weaves every hook its scenarios need (their hook groups and method selectors, each in one call) before it registers any of them, so a weaving failure starts none of them; it is recorded under the plan's handle id (`plan:<name>`, `session-plan:<name>`). The one refusal that is not recorded is the reloader's own check for an id taken elsewhere, which it retries on every tick.
